# Project Glossary

Status: active

This is the canonical terminology guide for public APIs, implementation names,
documentation, requirements, and tests. Plane names describe optical location;
product names describe the represented quantity. New scientific terms should be
defined here before they become public API.

## Naming Rules

- Do not combine a plane location and an assumed physical quantity in one type
  name. Use, for example, an `IntensityMap` whose metadata says `FocalPlane()`.
- State coordinate domain and units explicitly. Do not infer metres or radians
  from plane kind alone.
- Name every public untyped physical angle with its accepted unit suffix:
  `_rad`, `_deg`, or `_arcsec`. Documentation alone does not make an
  unsuffixed numeric angle unambiguous. Internal radian fields follow the same
  rule unless their enclosing type fixes the unit by construction.
- Use *rate*, *exposure*, and *count* according to whether time has not yet been
  integrated, has been integrated per area, or has been integrated per sample.
- Use *MTF* only for a frequency-domain modulation transfer function. A kernel
  applied to an image is a spatial-domain response model.
- Use *WFS signal* for a sensor-independent typed measurement. Use *slope* only
  when the values are wavefront gradients or calibrated centroid-equivalent
  slopes.

Package-architecture terms are used consistently as follows:

| Term | Project meaning |
|---|---|
| Canonical owner | The one Julia module that defines and maintains a supported binding or generic-function identity. Other modules import that identity and add methods where appropriate; they do not create parallel generics or root forwarding aliases. |
| API allowlist | The exact exported and qualified-`public` bindings maintained by one canonical owner. An allowlist is an equality contract, not a maximum-size budget or a representative sample. |
| Extension hook | A generic function intentionally extended by an optional package extension. The hook retains one canonical owner even when methods are supplied for several optional dependencies. |
| Cross-module import | An explicit import of a binding from its canonical owner for package-internal composition. It does not transfer ownership or make the binding public. |
| Definition | Cold, reusable configuration from which a run is prepared. A definition contains no prepared arrays, mutable run state, scratch, exact product binding, schedule, queue, or transport owner. |
| Execution plan | A run-immutable numerical or physical contract produced or validated during preparation. A plan may retain dimensions, mappings, coefficients, backend/device requirements, and a logically immutable reentrant operator, but not persistent scientific state, replaceable scratch, caller-visible products, or incidental exact-array identity. A type uses the `Plan` suffix only when it satisfies this contract. |
| Execution strategy | An immutable dispatch choice that selects how an operation is performed but does not own a prepared numerical contract. Use `Strategy`, `ExecutionStyle`, or a more specific accepted term rather than `Plan`. |
| Execution state | Persistent mutable values whose contents can affect a later scientific result. State has one writer and explicit reset, checkpoint, or replay semantics where those operations are supported. If discarding a value can change the next result, it is state rather than workspace. |
| Execution workspace | Replaceable scratch or execution resources used by a prepared operation. Recreating a workspace cannot change the deterministic physical trajectory. A stream-bound, task-bound, scratch-owning, or non-reentrant backend handle is workspace or prepared-owner state, not automatically part of a plan. |
| Product | A caller-visible scientific or integration result with explicit ownership and metadata. A product is not workspace merely because a mutating execution method writes it. |
| Prepared execution owner | A single-writer run owner that binds exact plan, state, workspace, input, output, and backend/device/context identities and validates those bindings before repeated mutation. A prepared owner may provide a convenient routine API, but it is not itself an algorithm plan solely because it was constructed during preparation. |
| Bounded prepared storage | Storage allocated to its admitted final capacity during preparation and unavailable for growth while armed. Boundedness is an owner and lifecycle invariant, not a property inferred from a low-level container type. Package code does not directly use Julia's `Memory`. Homogeneous armed host storage uses [FixedSizeArrays.jl](https://github.com/JuliaArrays/FixedSizeArrays.jl)'s `FixedSizeArray` with a concrete element type; a `Vector` may be used only as a cold builder before sealing. Heterogeneous storage uses tuples, concrete unions, family-grouped or purpose-built owners, while numerical device storage uses its native backend arrays. `FixedSizeArray` may encapsulate `Memory` internally on supported Julia versions; package code depends on the fixed-size array contract rather than that backing type. |
| Type-erased storage | A struct field or collection whose stored type is `Any`, an abstract type, or an uninstantiated parametric family. `Any`-typed storage is boxed and prevents the owner from expressing a concrete execution contract. It does not become suitable by changing its container; bounded heterogeneous execution requires concrete family groups, tuple/union/owner storage, or an explicit prepared function barrier with allocation and inference evidence. An unconstrained `::Any`, `<:Any`, or `Vararg{Any}` method signature is a dispatch wildcard rather than stored representation and is reviewed separately. |
| Algorithm graph | A finite, statically prepared composition of AOS-native graph nodes connected by named ndarray ports. A graph fixes node order, exact port formats, direct links, delayed links, startup sparse parameters, and caller-visible boundary storage before execution. It does not replace domain APIs, own optical topology or detector physics, advance wall time, or imply PipeWire deployment. |
| Algorithm graph adapter protocol | The qualified-public multiple-dispatch seam by which a scientific module or optional package makes one operation schedulable without changing its domain API. `graph_node_ports` declares fixed ports from construction config; `prepare_graph_node` creates one exact owner after storage and sparse-parameter admission; and `step_graph_node!` plus `reset_graph_node!` execute that owner. `enqueue_graph_node!` has a default implementation and may be specialized only when an adapter can preserve exact-context ordering while deferring completion. `graph_node_capture_capability` is a separate conservative trait for fixed-address CUDA Graph or HIP Graph replay. The protocol does not require Calculon, create a universal scientific `process!` API, or permit live topology mutation. |
| Algorithm graph config | Cold construction and graph-rebuild values that can affect port type, shape, schema, layout, or prepared resources. Config is admitted before graph storage is allocated and cannot change during a prepared run. It is distinct from scalar props and ndarray sparse parameters. |
| Algorithm graph props | Scalar initial values supplied to a graph node without changing its port contract. Version 1 TOML files admit initial props during preparation but do not provide live prop transactions. Large reconstructors, bases, masks, and calibration arrays are sparse parameters rather than props. |
| Algorithm graph TOML file | A versioned, human-authored declarative subset of the Julia graph API. It names node types from an explicitly supplied immutable type map, describes static topology with `node.port` endpoints, and refers to caller-supplied arrays through external binding names. It contains no Julia expressions, dynamic type lookup, file-format-specific calibration loading, scheduler tasks, or wall-clock policy. |
| REVOLT graph profile | A run-immutable selection made before graph preparation. `full_optical` uses the general coordinate-sampled provisional HSDM277 Gaussian implementation. `fast_dm` retains the same atmosphere, optical sampling, WFS propagation and modulation, detector model, external frame shape, HIL sequence, exact physical command order, and provisional Gaussian surface while exploiting the declared regular actuator grid for separable evaluation. The specialization is equivalent only while that provisional regular-grid registration remains authoritative; measured or irregular influence data requires the general or measured-influence node. Runtime overload never changes this selection. |
| Multilayer-atmosphere OPD graph node | The AOS-native graph adapter for one finite moving-screen `MultiLayerAtmosphere`. Preparation creates the phase screens and an on-axis infinite-source renderer on the graph's exact compute device. The prepared owner retains the evolving atmosphere and one explicit single-writer RNG stream. Each node invocation advances exactly one configured positive `atmosphere_step` and publishes one complete pupil-plane atmospheric OPD map in metres. It does not infer cadence from detector exposure or wall time, apply a deformable-mirror surface, add other path aberrations, or retain historical atmosphere epochs. |
| Shack–Hartmann photon-rate graph node | The AOS-native graph adapter for one diffractive Shack–Hartmann optical front end. It consumes a complete pupil-plane OPD map and writes a caller-owned, cell-integrated detector-plane photon-rate mosaic. Telescope aperture, guide-source radiometry, lenslet geometry, and focal-plane sampling are construction config. Detector exposure, noise, readout, centroid estimation, and acquisition cadence are separate operations rather than hidden behavior of this node. |
| Pyramid photon-rate graph node | The AOS-native graph adapter for one diffractive Pyramid optical front end. It consumes a complete pupil-plane OPD map and writes the four re-imaged pupils into one caller-owned, cell-integrated detector-plane photon-rate frame. Telescope aperture, guide-source radiometry, pupil sampling, phase-mask image geometry, and modulation quadrature are construction config. Detector exposure, noise, readout, differential estimation, and acquisition cadence are separate operations rather than hidden behavior of this node. |
| Pyramid modulation propagation strategy | The run-immutable choice used to evaluate a prepared Pyramid modulation quadrature. `PyramidPupilTiltStrategy` is the reference formulation: it applies every quadrature point as a pupil-plane phase tilt and performs one forward and one inverse propagation per point. `PyramidShiftedMaskStrategy` is a detector-product approximation for fixed prepared modulation: it propagates the unmodulated pupil to the focal plane once, applies one precomputed focal-plane Pyramid mask shifted for each quadrature point, and performs one inverse propagation per point. The shifted-mask strategy preserves the declared quadrature and photon-rate normalization but is not pointwise identical to the pupil-tilt formulation for fractional Fourier-grid shifts; it requires explicit validation for the admitted pupil sampling and aberration envelope. It does not apply to dynamic modulation updates unless its shifted masks are rebuilt. |
| CCD detector-acquisition graph node | The AOS-native graph adapter for one complete-frame, single-read CCD acquisition. It consumes a cell-integrated detector-plane photon-rate mosaic, owns one exact `PreparedDetectorAcquisition` and one explicit single-writer RNG stream, and writes a caller-owned detector frame. Exposure duration, quantum efficiency, photon noise, readout noise, binning, and the RNG seed are construction config. Partial exposure events, rolling shutters, frame transfer, and readout readiness require explicit Julia composition or a dedicated atomic node. |
| EMCCD detector-acquisition graph node | The AOS-native graph adapter for one complete-frame, linear-mode EMCCD acquisition. It consumes a cell-integrated four-pupil photon-rate frame, owns one exact `PreparedDetectorAcquisition` and one explicit single-writer RNG stream, and writes a caller-owned detector frame. Exposure duration, quantum efficiency, electron-multiplication gain and range, dark current, clock-induced charge, saturation, quantization, noise, binning, and the RNG seed are construction config. One graph step performs one sequential complete-frame acquisition; frame-transfer timing and readout readiness require explicit Julia composition or a dedicated atomic node. |
| Shack–Hartmann centroid graph node | The AOS-native graph adapter for calibrated center-of-gravity estimation from one complete lenslet-mosaic detector frame. It snapshots an explicit valid-subaperture mask and two-column reference signal as sparse ndarray parameters, then writes the canonical full `[axis 1; axis 2]` centroid-slope vector in Julia column-major lenslet order. Its `centroid_cutoff_fraction` is the OOPAO-compatible fraction of the global lenslet-spot peak below which pixels are zeroed; it is not SPECULA `ShSlopec.thr_value`, which subtracts an absolute pedestal before clamping. Invalid lenslets remain zero. Compact operational slope selection, detector ROI-offset interpretation, and reconstruction are separate nodes. |
| Shack–Hartmann slope-selection graph node | The AOS-native graph adapter that snapshots an explicit Shack–Hartmann lenslet order, consumes the full `[axis 1; axis 2]` measurement, and writes compact `[axis 1, axis 2]` pairs in that order. It performs only ordered selection and layout conversion: it does not parse detector ROI origins, change centroid units or signs, apply reference offsets, or claim compatibility with an external reconstructor. |
| Control-matrix reconstruction graph node | The AOS-native graph adapter around `Control.ControlMatrixPlan`. It snapshots one already calibrated dense control matrix from a startup sparse parameter, consumes one exact ordered WFS signal vector, and writes reconstructed controller coordinates. It adds no reference subtraction, slope reordering, inverse construction, controller state, command-basis expansion, or external-calibration compatibility claim. |
| Closed-loop correction graph node | The AOS-native graph adapter around `Control.ClosedLoopCorrectionPlan`. It atomically consumes the current reconstructed residual error and the preceding demanded-minus-realized correction in the same coordinate system, then publishes the complete demanded correction and integrator state. The first step starts from zero and ignores its required placeholder feedback buffer. Hidden-mode removal, coordinate transforms, command constraints, physical DM response, and feedback delay wiring remain explicit separate operations. |
| Deformable-mirror surface graph node | The AOS-native graph adapter around the physical `Optics.DeformableMirror` surface model. It consumes one complete PDM command, snapshots caller-bound measured actuator coordinates and sampled influence functions during preparation, applies the configured actuator-response model, and publishes one complete surface OPD. The node does not infer an actuator layout, influence width, controller coordinate map, atmosphere, optical-path placement, or command-arrival time. |
| Gaussian deformable-mirror surface graph node | The explicitly analytic AOS-native graph adapter around `Optics.DeformableMirror`. It consumes one complete vector of unit-peak actuator surface-OPD coefficients, snapshots caller-bound actuator coordinates in normalized pupil coordinates, evaluates Gaussian influence functions with one configured `influence_width`, and publishes their superposed complete surface OPD. Its command coefficients and output are optical path differences in metres; they are not normalized hardware commands or mirror-surface displacement. The node is a replaceable provisional model until qualified sampled influence functions are available. It does not infer command calibration, actuator coordinates, influence width, pupil registration, controller mapping, atmosphere, optical-path placement, or command-arrival time. |
| Grid Gaussian deformable-mirror surface graph node | The regular-grid specialization of the Gaussian deformable-mirror surface graph node. A startup sparse parameter maps every complete active PDM command element to one unique column-major cell of a declared square actuator grid. The prepared owner zero-fills inactive cells and evaluates the same Gaussian surface as the factored `X * C * Y'` product. This is equivalent to the general Gaussian sum only for the declared regular grid and separable registration; irregular coordinates, nonseparable misregistration, or measured influence functions require their corresponding general node. |
| Uncompensated pupil OPD | The complete pupil-plane optical path difference produced by the modeled path before the selected controllable PDM surface is applied. It may already contain atmosphere and static or dynamic aberrations. It is not a controller residual-error vector, and its name does not imply that other path-local optics have been omitted. |
| Pupil-OPD composition graph node | The AOS-native stateless graph operation that adds one complete sampled PDM surface OPD to one uncompensated pupil OPD and publishes one complete pupil-plane OPD on the same declared grid. It does not infer correction sign, surface-to-OPD scaling, conjugation, relay registration, resampling, or command timing; those facts must already be present in the supplied surface model and path binding. |
| Virtual deformable mirror (VDM) coordinates | Controller-facing deformable-mirror coordinates used to combine commands independently of a particular physical actuator layout. The *active VDM* contains coordinates directly controlled in a run; the *full VDM* may additionally contain explicitly extrapolated or otherwise completed coordinates required by a physical-DM projection. A VDM is a coordinate model, not an optical surface or hardware device. |
| Physical deformable mirror (PDM) coordinates | Concatenated commands in the declared order of physical DM actuators. A PDM command becomes a physical optical response only when an explicit deformable-mirror model consumes its demanded values. |
| Controller-to-VDM projection | An already calibrated linear map from concatenated controller-command coordinates into one active VDM coordinate vector. It does not perform integration, command conditioning, or physical surface formation. |
| VDM-to-PDM projection | An already calibrated two-stage map from active VDM coordinates through full VDM coordinates into concatenated physical-actuator coordinates. The active-to-full map makes extrapolation or completion explicit; the full-VDM-to-PDM map makes hardware projection explicit. |
| PDM actuator range conditioning | Per-actuator interval clipping that publishes a demanded PDM command and `requested - demanded` constraint feedback. The current AOS operation implements only these prepared lower and upper ranges; it does not imply slew, quantization, command-power, inter-actuator-stroke, or stroke-optimization constraints. |
| PDM-to-VDM feedback projection | The reverse, explicitly calibrated two-stage map from PDM constraint feedback through full VDM coordinates into active VDM coordinates. It is not inferred as a matrix inverse during graph preparation. |
| VDM-to-controller feedback projection | An already calibrated map from active-VDM constraint feedback into concatenated controller coordinates. A graph uses a delayed link when this result is feedback for the next complete controller step. |
| Proper propagation graph node | The optional graph-node adapter supplied by `AdaptiveOpticsProperHIL.jl` for one Julia-native `Proper.jl` prescription. It accepts complete-frame pupil OPD and pupil-amplitude ndarrays on one square propagation grid, retains separately owned random state and prescription scratch, and writes one separately declared, potentially rectangular output ndarray as an atomic node invocation. The prescription owns any prepared crop, resampling, detector mapping, and output units. One prepared node uses one numeric type and exact compute device. It does not make `Proper.jl` a core dependency, infer detector semantics from dimensions, insert a host/device transfer, schedule an acquisition cadence, or by itself make Julia code loadable by PipeWire. |
| Direct algorithm link | A same-step connection from one algorithm output port to one later algorithm input port. The linked ports have identical element type, logical shape, scientific schema, and native layout. Declaration order is execution order in the portable graph, so a direct link never creates a feedback cycle. |
| Delayed algorithm link | An explicit connection whose consumer reads the value committed after the preceding successful graph step. Its prepared state owns the initial value and bounded copy storage. A delayed link breaks a feedback dependency; it is not a queue, an implicit sample-and-hold policy, a physical command delay, or permission to expose a partially completed scientific operation. |
| Prepared algorithm graph | `AlgorithmGraphs.PreparedAlgorithmGraph`: the single-writer prepared owner of a concrete tuple of prepared algorithm nodes, their exact input/output bindings, delayed-link state, and graph boundary products. Preparation admits every format and connection before an adapter may bind an exact node execution owner to the final buffers. `AlgorithmGraphs.step_graph_async!` submits every node once in validated declaration order; `wait_graph_step!` observes completion and publishes delayed-link and sequence state. `step_graph!` combines those boundaries. It owns no task, worker, dynamic scheduler, wall clock, PipeWire object, or hidden physical event calendar. |
| Graph step ticket | `AlgorithmGraphs.GraphStepTicket`: the single-use proof that one submitted complete graph frame owns the prepared graph's mutable node state, workspaces, inputs, outputs, delayed-link storage, RNG state, and retained execution context until `wait_graph_step!` succeeds or fails. One graph has capacity for exactly one pending ticket. A ticket is not a task, frame-storage slot, transport buffer, or permission to submit another frame. |
| Captured graph execution | `AlgorithmGraphs.CapturedGraphExecution`: an opt-in preparation policy that records one complete graph step—the qualified node sequence followed by delayed-link commits—as one native CUDA Graph or HIP Graph executable. Every node owner must qualify; there is no direct-stream fallback inside a captured graph. Capture eligibility requires fixed storage identity, device-resident evolving replay state, and no host scientific-state mutation, dynamic execution-storage allocation, synchronization, or result query in the recorded device operation. Julia compilation, backend recording, and native graph instantiation are cold preparation work; replay uses the retained executable and bounded completion hooks. It is whole-step device-command capture, not multi-frame buffering or permission to freeze model time or RNG state. |
| Graph HIL lockstep boundary | `AlgorithmGraphs.PreparedGraphHILBoundary`: the transport-neutral, single-writer adapter that binds one prepared graph's complete command input and frame output to distinct caller-visible host exchange buffers. The first frame uses the graph's snapshotted sequence-zero command. A completed frame with sequence `n` must receive one complete, finite command with the same sequence before the next frame can run; successful adoption makes that command active for frame `n + 1`. Validation completes before the exact-target command buffer is mutated, and host/device copies complete before publication or adoption returns. The boundary owns no task, queue, socket, timeout, command-hold policy, wall clock, or PipeWire object. |
| Model-time driver | A deterministic caller-owned policy that selects graph-step timestamps on canonical model time. A fixed-step driver advances by one positive constant duration. A prepared-boundary driver advances directly between an immutable finite or periodic set of admitted physical boundaries. Neither driver measures execution time or paces against a wall clock. |

## Optical Planes, Coordinates, And Products

| Term | Project meaning |
|---|---|
| Pupil plane | A transverse plane conjugate to the aperture stop. Represented by `PupilPlane()`. |
| Focal plane | A physical focus or focal-mask plane. Represented by `FocalPlane()`. Its coordinates may be angular when that is the declared propagation output. |
| Pupil-plane placement | The declared optical location of a component in a plane conjugate to the aperture stop, represented by `PupilPlane()` metadata or explicit application topology. It is optical placement, not CPU/GPU placement, command cadence, or controller grouping. |
| Atmospheric-conjugate placement | A geometric component plane conjugate to a finite nonnegative altitude above the entrance pupil, expressed in metres. The altitude participates in a source-footprint transform; by itself it is not a diffractive relay prescription. |
| Focal-plane placement | The declared location of a component at a physical focus or focal-mask plane, represented by `FocalPlane()` metadata or explicit application topology. |
| Path visibility | An immutable application or graph declaration of which optical branches contain a component. Visibility does not imply cadence, controller grouping, or execution-resource placement. |
| Source footprint | The pupil-domain region and coordinate mapping intercepted by a source ray bundle at a declared conjugate altitude. It depends on source direction and, for a finite-height LGS, cone scaling, then on any explicitly declared pupil-relay registration. Declaring a conjugate altitude does not itself implement this transform. |
| Sodium-layer profile | `Optics.SodiumLayerProfile`: a sampled laser-guide-star sodium-layer return model defined by positive geometric altitudes in metres and nonnegative relative photon-return weights with a positive finite total. The weights are proportional samples used by the implemented elongation model; they are not an absolute sodium number-density calibration or an atmospheric-layer turbulence profile. An `LGSSource` may omit this profile and remain a finite-height laser guide star. |
| Pupil-relay registration | The cold affine registration from geometric source-footprint coordinates to one sampled pupil-surface grid. It declares magnification, rotation, parity, and decenter; sampled-plane origin, sampling, axis order, and axis signs remain properties of `OpticalPlaneMetadata`. This path/relay geometry is distinct from `Misregistration`, which acts inside DM surface formation. |
| Atmosphere reference wavelength | `reference_wavelength_m`: the wavelength in metres at which an atmosphere model's Fried parameter `r0` and generated phase in radians are defined. Atmosphere rendering converts that phase to wavelength-independent OPD by multiplying by `reference_wavelength_m / (2π)`; later field formation converts OPD to phase at the source wavelength. It is not implicitly the guide-source or science-source wavelength. |
| Atmosphere wind direction | `wind_direction_deg`: the direction of an atmosphere layer's wind-velocity vector in degrees. The implemented components are `wind_velocity_x = wind_speed * cosd(wind_direction_deg)` and `wind_velocity_y = wind_speed * sind(wind_direction_deg)`. It is distinct from source direction and telescope pointing. |
| Telescope-spider position angle | Each value in `apply_spiders!(...; angles_deg=...)` is the position angle of one spider centreline in degrees in the sampled pupil coordinates. `SpiderMask(...; angle_rad=...)` is the corresponding single-mask primitive in radians. |
| Deformable-mirror misregistration | `Misregistration` is the affine registration applied to actuator coordinates during deformable-mirror surface formation. Its rotation is declared by `rotation_deg`; the orientation of its anisotropic scaling axes is declared by `anamorphosis_angle_deg`. Both are angles in degrees, while `shift_x` and `shift_y` retain the deformable mirror's actuator-coordinate convention. |
| Prepared pupil-footprint coupling | An immutable path-local mapping from one exact prepared pupil input to a compatible sampled pupil-surface grid. An application may use an identity same-grid path or a finite-support affine sample mapping for a source direction and conjugate altitude. The coupling owns no command state, surface state, cadence, or transport. |
| Image plane | An image-forming plane. Use this term in prose when the distinction from a focal-mask plane matters; introduce a concrete marker only with an implemented contract. |
| Detector plane | The optical sampling plane incident on a detector, represented by `DetectorPlane()`. It is not the detector readout frame itself. |
| Intermediate plane | A known transverse optical plane that is not more specifically a pupil, focal, image, or detector plane. Represented by `IntermediatePlane()`; do not use *propagation plane*. |
| Metric coordinates | Plane `sampling` and `origin` are in metres. Represented by `MetricCoordinates()`. |
| Angular coordinates | Plane `sampling` and `origin` are in radians. Represented by `AngularCoordinates()`. |
| Normalized pupil coordinates | Dimensionless coordinates normalized to the entrance-pupil diameter, represented by `NormalizedPupilCoordinates()`. For a re-imaged-pupil detector mosaic they describe the optical relay sampling, not a manufactured detector's physical pixel pitch. |
| Sample-centered | A geometric origin lies on a stored sample. |
| Inter-sample-centered | A geometric origin lies between stored samples. This is not necessarily an inter-pixel convention. |
| Telescope definition | `Optics.TelescopeDefinition`: an immutable, configuration-only declaration of the currently supported annular telescope aperture. It contains scalar aperture geometry, scalar pupil reflectivity, numeric type, and an explicit revision, but no sampled arrays, mutable state, array backend, or compute device. `prepare_telescope(definition, target)` materializes its numerical `Telescope` on one exact compute device. |
| Telescope aperture | The revisioned support, intensity reflectivity, diameter, and spatial sampling prepared by `TelescopeAperture`. It is geometry shared while paths are prepared; it is not a mutable wavefront or OPD buffer. |
| Pupil function | The complex pupil transmission in Fourier optics. `PupilFunction` snapshots one telescope-aperture revision, stores its wavelength-independent support and field amplitude, and owns the mutable OPD for one path; field formation realizes the wavelength-specific complex pupil. |
| Pupil reflectivity | The finite dimensionless intensity-throughput fraction in `[0, 1]` stored by `TelescopeAperture`. Optical field formation applies its square root as an amplitude transmission. It is not an amplitude coefficient itself. |
| Electric field | In this package, a scalar complex optical field envelope/phasor sampled on a declared plane. `ElectricField` is not an SI vector electromagnetic field in V/m unless its metadata explicitly establishes such a normalization. |
| Intensity | The computational quantity `abs2(E)`. Its physical units and normalization follow the field and metadata; the word alone does not assert radiometric irradiance. |
| Intensity map | A real sampled array of intensity values plus `OpticalPlaneMetadata`, represented by `IntensityMap`. The metadata, not the type name, states plane location and physical semantics. |
| Photon-arrival-rate intensity map | An `IntensityMap` with `PhotonRateNormalization()` and an explicit spatial measure. It represents a rate before detector exposure: either a spatial density or a rate integrated over each represented cell. |
| Direct imaging | Native image formation from a declared pupil function or preformed pupil-plane electric field to a caller-owned focal-plane photon-arrival-rate `IntensityMap`. `prepare_direct_imaging` fixes storage, grid, backend, device, and workspace; `form_direct_image!` executes without applying detector exposure duration. The current off-axis model resolves a finite integer displacement during preparation, honors the focal grid's declared `:x`/`:y` axis order and signs, and applies a periodic shift. |
| Direct-imaging batch | A prepared native Fraunhofer execution group for an ordered set of compatible physical direct-science source samples. It owns one stacked field workspace, one stacked photon-arrival-rate allocation, and one FFT plan over the two optical axes while exposing each sample as an ordinary focal-plane `IntensityMap` view in an `OpticalProductBundle`. Direction and wavelength remain sample metadata; the batch performs no coherent source combination, spectral integration, detector exposure, implicit resampling, host transfer, or runtime regrouping. |
| Optical path difference (OPD) | Scalar optical path-length difference in metres. Positive-sign convention must be validated at integration boundaries. |
| Modal OPD expansion | A prepared linear combination of dimensionless pupil-plane basis modes by modal coefficients expressed in metres, masked by pupil support to produce one OPD map. `Calibration.ModalOPDExpansionPlan` owns the run-immutable basis and pupil-support snapshots; each evaluation writes a complete caller-owned OPD output and owns no persistent state or scratch workspace. |
| Sampled aberration | A fixed sampled OPD perturbation represented by native `NCPA` or `OPDMap` storage with exact `OpticalPlaneMetadata`. An application or graph branch declares placement, visibility, additive/replacement semantics, registration, and exact-target preparation. It is not a controllable device or a cadence-bearing state owner. |
| Point-spread function (PSF) | The image-plane response to a point source under an explicitly declared normalization. A source-brightness- and exposure-scaled image is not intrinsically a PSF. |
| On-axis Strehl ratio | The intensity at the nominal science-axis coordinate divided by the exact diffraction-limited peak for the same aperture and flux. Unlike a recentered peak Strehl ratio, it includes image motion from residual tip and tilt. A sampled focal-plane pixel is not assumed to coincide with the optical axis. |
| Non-common-path aberration (NCPA) | Aberration visible to one optical branch but not to its reference or sensing branch. `Optics.NCPA` is the physical sampled OPD map in metres; KL/Zernike/M2C basis selection and coefficient generation are calibration policy. Model the resulting optic in the branch where it physically occurs. |

`UnspecifiedSpectralCoordinate()` means that no spectral coordinate has yet been
declared; it does not mean wavelength independence.
`AchromaticSpectralCoordinate()` explicitly declares wavelength-independent
geometry or data. `MonochromaticChannel(λ)` declares one wavelength in metres.
`IntegratedSpectralChannel(id)` declares that values have already been integrated
over an application-defined passband identified by `id`; equal identifiers are
the compatibility contract, while the passband definition remains application
owned.

## Radiometry And Photon Quantities

| Term | Unit and use |
|---|---|
| Radiant irradiance | Incident radiant flux density, W·m⁻². Use *irradiance* without a photon qualifier only when this radiometric meaning is intended. |
| Photon irradiance | Incident photon-rate density, photons·s⁻¹·m⁻². `photon_irradiance(source)` uses this quantity. |
| Spectral sample weight | The normalized photon-number fraction of `photon_irradiance(source)` assigned to one `SpectralSample` in a `SpectralBundle`. It is not a radiant-energy fraction. Ordinary bundle constructors normalize nonnegative proportional input weights to sum to one. |
| Photon flux | Photon rate, photons·s⁻¹, integrated over a stated receiving area or channel. Do not use it for a per-area source value. |
| Photon-arrival-rate product | Detector-facing umbrella term when metadata may declare either a spatial density or a cell-integrated photon rate. |
| Photon exposure | Time-integrated photon irradiance, photons·m⁻². |
| Expected photon count | Expected photons integrated over both time and represented cell area. It is the mean supplied to photon-counting statistics. |
| Relative or normalized intensity | Dimensionless intensity under a declared normalization, such as unit total power, peak, or contrast. It cannot enter a physical detector acquisition without an explicit scaling contract. |
| Point-sampled measure | `PointSampledMeasure()`: each value is evaluated at a coordinate and includes no represented cell area. It cannot enter detector acquisition without an explicit spatial mapping or integration. |
| Spatial-density measure | `SpatialDensityMeasure()`: each value is per unit area of the declared coordinate domain. Detector acquisition multiplies it by the represented cell area before exposure integration. A photon-rate density on metric coordinates is photon irradiance. |
| Cell-integrated measure | `CellIntegratedMeasure()`: each value has already been integrated over its represented spatial cell. A photon-rate-normalized value therefore has units photons·s⁻¹ per cell. |
| Coherent field combination | `CoherentFieldCombination()`: compatible complex fields may be combined before intensity formation, so relative phase is retained. |
| Incoherent intensity addition | `IncoherentIntensityAddition()`: compatible intensity maps may be added elementwise after their grid, spectral, radiometric, backend, and device contracts have been checked. |
| Non-combinable product | `NonCombinableProduct()`: the product must remain separate unless an explicit physically justified mapping is prepared. |
| Optical product bundle | `OpticalProductBundle`: a typed, fixed-cardinality collection that preserves products on incompatible grids or channels without implicit resampling, radiometric conversion, or accumulation. Its container cannot grow or shrink; a prepared execution owner independently binds the exact ordered members and rejects replacement before numerical mutation. Each leaf's caller-owned numerical array remains mutable. |
| Normalized test source | A source carrying `NormalizedTestSource()` radiometry and dimensionless relative power. It is useful for calibration and deterministic tests, but does not claim physical photon irradiance and requires an explicit scale before physical detector acquisition. |

The detector boundary distinguishes photon-rate density from cell-integrated
photon rate. The WFS optics stage applies no elapsed-time factor. A prepared
detector acquisition validates the map metadata, applies the presampling
response before physical-pixel integration, and integrates its explicit
exposure duration exactly once. Incompatible maps remain separate in an
`OpticalProductBundle` unless an explicit conversion is prepared.

The definitions of [irradiance](https://cie.co.at/eilvterm/17-21-053),
[photon irradiance](https://cie.co.at/eilvterm/17-21-058),
[photon flux](https://cie.co.at/eilvterm/17-21-040), and
[photon exposure](https://cie.co.at/eilvterm/17-21-073) follow the CIE
International Lighting Vocabulary.

## Detector Response

| Term | Project meaning |
|---|---|
| Presampling detector response | A spatial-domain response applied before discrete detector sampling or binning. `GaussianPixelResponse`, `SampledFrameResponse`, and `RectangularPixelAperture` are response models. A sampled kernel is a centered discrete impulse response: its positive row and column offsets appear at the same offsets from an input impulse. |
| Detector acquisition plan | `Detectors.DetectorAcquisitionPlan`: the run-immutable numerical and radiometric contract for one compatible frame-detector configuration and immutable `IntensityMap` description. It owns detector parameters, input metadata and shapes, output shapes, photon-rate scaling, and declared-channel QE. It owns no live detector, mutable input storage, persistent detector state, workspace, or product. |
| Detector acquisition state | Persistent mutable detector values that can affect a later scientific result: accumulated charge, persistence state, thermal state, integrated duration, and readiness where applicable. State has one writer and is not replaceable scratch. |
| Detector acquisition workspace | Replaceable scratch and execution resources used by detector response, physical-pixel integration, temporal sampling, stochastic response, host staging, and readout fitting. Recreating compatible workspace cannot change a deterministic trajectory. |
| Detector acquisition products | Caller-visible detector results, including the integrated frame, converted output, and configured readout products. Readout cubes, fit values, and read offsets in seconds are products; intermediate averages and full-frame fitting arrays are workspace. A kernel may write directly into a product without making that product scratch. |
| Prepared detector acquisition | `Detectors.PreparedDetectorAcquisition`: the exact single-writer binding of one frame detector, one mutable `IntensityMap` storage identity, its detector acquisition plan, persistent state, replaceable workspace, and caller-visible products. `prepare_detector_acquisition` validates current finite nonnegative input samples, plane, radiometry, spatial measure, declared-channel QE, shapes, backend, compute device, and forbidden aliases before publishing the owner. Repeated `capture!` trusts later producer writes to the bound input storage; replacing a bound owner requires preparation again. |
| Event-driven detector acquisition | A prepared virtual-time lifecycle over one exact prepared detector acquisition. Global-shutter, rolling-shutter, and frame-transfer definitions retain immutable timing; their prepared lifecycles bind that acquisition, grant exactly one separately owned mutable lifecycle state, and use fixed-cardinality `FixedSizeVector` read-offset schedules. Begin, half-open interval accumulation, row-band transition or nondestructive read, close or image-to-storage transfer, readout completion, and readiness are explicit transitions where applicable. |
| Half-open exposure | An exposure interval `[start, close)`: optical samples at `start` are included, while a sample timestamped exactly at `close` is excluded. Exact integer model-time boundaries, rather than floating accumulated-time tolerance, should determine membership and completion. |
| Exposure duration | The elapsed interval during which a detector integrates its incident photon-arrival-rate product. `DetectorParams.exposure_duration` is the detector's configured interval in seconds. It is not an absolute timestamp, start-to-start cadence, readout duration, or incremental integration duration. |
| Acquisition duration | The modeled elapsed interval from acquisition start through the sensor operations required to complete one acquisition. Depending on the sensor and acquisition mode, it can include exposure, rolling-shutter sequencing, frame transfer, or nondestructive reads. It is model time, not host wall-clock execution time, a product-readiness timestamp, or a sample period. |
| Readout duration | The modeled elapsed interval required for one declared detector readout operation. `HgCdTeReadout.read_duration` describes one full-sensor read and is distinct from exposure duration, total acquisition duration, and the offsets of individual read products. |
| Integration duration | The positive duration in seconds over which one detector-facing photon-arrival-rate sample contributes to an exposure. The current incremental convenience API names this `integration_duration`; it is neither an absolute sample timestamp nor the sample period between consecutive samples. A virtual-time scheduler owns the interval boundaries. |
| Nondestructive read | A detector read that observes accumulated charge without ending or resetting the active integration. A scheduled up-the-ramp model records the charge state at each declared read event; a post-exposure cube synthesized from one final frame is a lower-fidelity convenience, not a time-resolved nondestructive-read simulation. |
| Skipper CCD sample duration | `CCDSensor.sample_duration`: the elapsed duration assigned to one configured full-frame nondestructive sample in `SkipperSampling`. Total sampling duration is the product of this duration and the fixed sample count. It is not a sample period, a whole conventional-CCD readout duration, or a model of the correlated-double-sampling electronics integration window. |
| Sample period | The start-to-start cadence between consecutive samples or acquisitions. A sample period can exceed the operation's sample or acquisition duration and is not inferred from either one unless a specific scheduling contract says so. |
| InGaAs area sensor | An area detector using indium gallium arsenide photosensitive material. `InGaAsSensor` supplies product-neutral glow and optional frame-to-frame persistence behavior while the owning `Detector` supplies dark current, QE, defects, nonlinearity, saturation, gain, and any explicit presampling response. The technology name does not imply a wavelength response, pixel aperture, blur, MTF, IPC, readout mode, or camera profile. |
| Frame-to-frame exponential persistence | `ExponentialPersistence(coupling, decay)`: a discrete latent-signal recurrence. For the sensor-defined frame \\(q_k\\) and latent state \\(l_k\\), \\(l_{k+1}=\\mathrm{decay}\\,l_k+\\mathrm{coupling}\\,q_k\\); \\(l_k\\) is added to the next frame. The dimensionless coefficients apply once per completed frame. They do not define an elapsed-time constant, exposure scaling, trap population, calibrated detector persistence, or a universal pipeline boundary. For `InGaAsSensor`, \\(q_k\\) is specifically the post-nonlinearity, post-saturation, post-charge-coupling frame before read noise, conversion gain, correction, quantization, and background subtraction. |
| Conventional HgCdTe array | An area detector using mercury-cadmium-telluride photosensitive material without avalanche multiplication in the modeled signal path. `HgCdTeSensor` composes the product-neutral `HgCdTeReadout` configuration for single, averaged nondestructive, correlated-double, Fowler, or up-the-ramp sampling. |
| HgCdTe linear-avalanche photodiode array | An HgCdTe area detector operated with linear avalanche multiplication. `HgCdTeAvalancheArraySensor` adds explicit avalanche gain, an excess-noise factor, and a multiplication model to the shared HgCdTe readout contract; it is distinct from a Geiger-mode SPAD/counting detector. |
| Linear-mode APD channel detector | `LinearAPDDetector`: one analog avalanche-photodiode element or a fixed bank of independent channels. `SingleElementLinearAPD` accepts scalar or one-element-vector photon flux; `LinearAPDChannelBank(n)` accepts exactly `n` photon-flux channels. Storage and output are one-dimensional and do not imply pixels or an area frame. This regime is distinct from Geiger-mode SPAD counting. |
| SPAD accumulated-count array | `SPADArrayDetector((rows, columns); ...)`: a fixed-shape area detector whose input is an already cell-integrated photon-arrival rate. It produces one accumulated expected-count or sampled-count image per exposure. It is not a photon-event stream and does not model avalanche timestamps, energy, time-over-threshold, or per-event correlations. |
| Active-area detection efficiency | `SPADArraySensor.active_area_detection_efficiency`: the expected fraction of photons incident on the photosensitive area that trigger accepted detections before dead-time loss. The separately declared fill factor scales the geometrical active fraction once. Neither scalar implies a wavelength curve or a pixel-aperture MTF. |
| MKID accumulated-count array | `MKIDArrayDetector`: an area detector whose matrix input is an already cell-integrated, spectrally prefiltered photon-arrival rate. It produces one accumulated expected-count or sampled-count image per exposure. It does not produce photon-arrival timestamps or per-photon energy estimates. Optional physical characteristics belong to `MKIDArrayCharacteristics` and do not change that observable boundary. |
| Energy resolving power | `MKIDArrayCharacteristics.energy_resolving_power`: the optional dimensionless physical characteristic \(R=E/\Delta E\). It is detector metadata, not an energy estimate and not evidence that the accumulated-count image resolves individual photon energies. |
| Photon-arrival-time resolution | `MKIDArrayCharacteristics.photon_arrival_time_resolution_s`: an optional positive detector characteristic in seconds. It is not a simulated timestamp, trigger jitter, integration duration, or sample period. |
| MKID wavelength passband | `MKIDArrayCharacteristics.wavelength_passband_m`: an optional inclusive `(minimum, maximum)` source-wavelength interval in meters. Source-aware capture filters scalar and weighted spectral sources against it. Matrix-only capture assumes the producer already applied spectral filtering. This scalar passband is not a calibrated wavelength-dependent QE curve. |
| Counting dead-time mean response | A deterministic map from the pre-dead-time expected count per live integration to its post-dead-time expectation. `NonParalyzableDeadTime` uses \(\mu/(1+\mu\tau/t_\mathrm{live})\); `ParalyzableDeadTime` uses \(\mu\exp(-\mu\tau/t_\mathrm{live})\). The optional Poisson stage samples the resulting expectation and is an explicitly lower-order surrogate for the true non-Poisson dead-time count distribution. |
| First-order afterpulse mean response | `FirstOrderAfterpulseMeanResponse(a)`: a deterministic accumulated-count approximation that multiplies the expected detections by \(1+a\), where `a` is the nonnegative mean number of first-order afterpulse counts per detection. It does not simulate avalanche history, afterpulse delay, higher generations, or the resulting overdispersed count statistics. |
| Nearest-neighbor count redistribution | `NearestNeighborCountRedistribution(f)`: a deterministic, count-conserving image operation that retains fraction \(1-f\) in each source cell and divides fraction \(f\) across that source cell's orthogonal in-bounds neighbors. It is an explicit reduced response, not a claim of optical blur, electrical crosstalk, SPAD avalanche propagation, or detector MTF. |
| Avalanche excess-noise factor | For one input carrier with stochastic multiplication \(M\), the dimensionless factor \(F=\mathrm{E}[M^2]/\mathrm{E}[M]^2=1+\mathrm{Var}(M)/\mathrm{E}[M]^2\). For input charge \(q\) whose carriers multiply independently, the implemented input-referred multiplication variance is \((F-1)q\), before multiplication by the square of the mean avalanche gain. This detector-literature definition is used by the linear-mode APD and HgCdTe avalanche models; it is not the EMCCD API's input-referred standard-deviation factor. |
| Conditional-Gamma avalanche multiplication | `Detectors.ConditionalGammaAvalancheMultiplication`: a nonnegative CPU reference model in which input-referred multiplied charge conditional on \(q>0\) is Gamma distributed with shape \(q/(F-1)\) and scale \(F-1\); \(F=1\) is deterministic. It models independent multiplication of input carriers and is not a photon-counting or timestamp model. |
| Clipped-Gaussian avalanche multiplication approximation | `Detectors.ClippedGaussianAvalancheMultiplicationApproximation`: a backend-portable approximation to conditional avalanche multiplication, \(q'=\max(q+\sqrt{(F-1)q}Z,0)\) for standard-normal \(Z\). Qualification is restricted to the moderate-charge regime \(q/(F-1)\geq25\), where truncation is negligible; lower-charge output is computationally defined but not claimed as a faithful multiplication distribution. |
| Synthesized final-charge ramp | The lower-fidelity direct-`capture!` up-the-ramp product labeled `:synthesized_final_charge`. It scales one completed charge realization to evenly spaced read offsets in seconds before fitting and cannot represent intra-exposure optical changes. |
| Time-resolved evolving-charge ramp | A nondestructive-read product in which each read snapshots charge accumulated through its explicit model timestamp, including irregular spacing. This requires explicit model composition and is distinct from a final-charge ramp synthesized after exposure. |
| Rolling-shutter row band | One contiguous prepared group of detector rows sharing open and close timestamps. `RollingShutterAcquisitionState` retains only bounded opened- and closed-band cursors. In rolling exposure, bands open and close in sequence with equal nominal exposure; in global reset exposure, every band opens together and later bands close later. |
| Rolling-shutter exposure-start offset | The elapsed seconds from the start of a modeled frame acquisition to the beginning of one row band's exposure. Temporal frame-source callbacks receive this offset; it is not an absolute timestamp, line duration, exposure duration, or readout-completion time. |
| Frame output window | `FrameWindow`: the rectangular region copied from a completed full detector frame into the reusable output product. It does not change exposed sensor geometry, row-band timestamps, or acquisition duration. Model a physically cropped sensor region with the corresponding detector frame dimensions. |
| CMOS shared row and column noise | Independent zero-mean Gaussian readout offsets drawn once per row or once per column for each completed frame, then shared by every pixel in that row or column. Their spatial covariance differs from both uniform independent read noise and the heteroscedastic independent `CMOSReadNoiseMap`; temporally correlated 1/f and random-telegraph noise are separate, unimplemented models. |
| Frame-transfer storage area | The light-shielded detector storage region that receives a completed EMCCD image-area exposure before serial readout. `PreparedFrameTransferAcquisition` models one non-aliasing storage-frame capacity, allowing the image area to integrate the next frame while that storage frame is read. It changes acquisition timing, not optical response or detector MTF. |
| Readout completion / product readiness / acquisition readiness | Readout completion finalizes a complete detector product at its declared model timestamp. Product readiness records when that complete product is available to its caller-owned destination. Acquisition readiness is the distinct transition that permits another exposure. A frame-transfer image area may already be integrating while the preceding storage product completes readout. |
| Pixel aperture | The photosensitive spatial support and fill factor of one pixel. `RectangularPixelAperture` is separable in the implemented rectangular case, but its detector-grid kernel does not claim continuous subpixel geometry; that requires an explicit oversampled optical-grid mapping. |
| Optical transfer function (OTF) | The complex spatial-frequency response associated with an imaging response. |
| Modulation transfer function (MTF) | The magnitude of the OTF. `detector_mtf` is the normalized interior, infinite-grid transfer magnitude of the realized discrete response kernel, in cycles per detector pixel. A finite detector uses zero extension and therefore has boundary-dependent response rather than one global MTF. The diagnostic does not claim the continuous subpixel-aperture MTF; that requires an explicit oversampled optical-grid mapping. No spatial kernel type is itself named an MTF. |
| Quantum efficiency (QE) | Expected collected signal carriers per incident photon under the declared spectral model. |
| PRNU / DSNU | Pixel-response nonuniformity / dark-signal nonuniformity. |
| Clock-induced charge (CIC) | Spurious charge generated by detector clocking. `clock_induced_charge_per_frame` is the implemented independent Poisson expectation in electrons per pixel per completed frame; it is not a per-second rate and is not scaled by exposure duration. |
| EMCCD excess-noise factor | The input-referred factor \(F \ge 1\) by which stochastic electron multiplication increases the shot-plus-background variance in linear operation. The conditional multiplication variance factor used by the implemented models is \(\sqrt{F^2-1}\), optionally bounded below by the model's declared minimum factor. |
| Conditional-Gamma multiplication | The CPU-only `ConditionalGammaMultiplication` model: for input charge \(q>0\), effective conditional factor \(f>0\), and mean gain \(g\), output is Gamma-distributed with shape \(q/f^2\) and scale \(g f^2\). Zero factor is deterministic gain. This is a conditional high-gain multiplication model, not a stage-by-stage register simulation. |
| Clipped-Gaussian multiplication approximation | The backend-portable `ClippedGaussianMultiplicationApproximation`: conditional output is \(g\max(q + f\sqrt{q}Z, 0)\) for standard-normal \(Z\). It is a nonnegative moment approximation intended for moderate-to-high charge, not the conditional-Gamma distribution and not a low-charge photon-event model. |
| EMCCD photon-counting output | A binary, coincidence-limited frame produced by thresholding the post-multiplication/read-noise value and then applying the configured Bernoulli detection efficiency. Multiple accepted photoelectrons in one pixel and frame still produce one output event. |
| Interpixel capacitance (IPC) | Post-collection capacitive charge coupling between detector nodes, not a presampling optical blur. |

CCD, EMCCD, CMOS, sCMOS, quantitative low-noise CMOS, InGaAs, conventional
HgCdTe, HgCdTe linear-avalanche photodiode arrays, Skipper CCD, SPAD, MKID, and linear-mode APD
describe detector technology or readout families. Configured CMOS variants
share the CMOS architecture in core; named commercial camera profiles belong
in a companion package. A single-element linear-mode APD is a channel detector and is not
forced into an area-frame API.

| Backends namespace | `AdaptiveOpticsSim.Backends` owns semantic backend selection, concrete compute-device identity, compatible allocation, reductions, random helpers, kernel launch, and synchronization. It does not own AO physics or graph topology. |
| Optics namespace | `AdaptiveOpticsSim.Optics` owns apertures, telescopes, sources, optical-plane metadata and products, propagation, direct imaging, sampled OPD, NCPA, deformable mirrors and other controllable optics, and reusable physical WFS components. |
| Atmospheres namespace | `AdaptiveOpticsSim.Atmospheres` owns atmosphere definitions and state, source-direction rendering and batching, and atmosphere-coupled propagation. |
| Detectors namespace | `AdaptiveOpticsSim.Detectors` owns detector response, sensor families, shutter and readout behavior, prepared acquisition, and detector products. |
| WavefrontSensors namespace | `AdaptiveOpticsSim.WavefrontSensors` owns composed WFS optical front ends, observations, measurements, detector bindings, estimators, geometric slopes, and LiFT. |
| Calibration namespace | `AdaptiveOpticsSim.Calibration` owns interaction and control matrices, modal bases, inverse policies, fitting, identification, optical-gain calibration, and model-derived NCPA synthesis. |
| Control namespace | `AdaptiveOpticsSim.Control` owns reconstruction, controller composition, delay lines, and prepared runtime control operations. |
| Tomography namespace | `AdaptiveOpticsSim.Tomography` owns guide-star geometry, atmospheric reconstruction, fitting, and DM-command projection. |
| Ensembles namespace | `AdaptiveOpticsSim.Ensembles` owns coarse-grained independent runs and optional offline scheduling policies. It is not an RTC deadline scheduler. |
| AlgorithmGraphs namespace | `AdaptiveOpticsSim.AlgorithmGraphs` owns static graph definitions, the AOS-native node adapter protocol, direct and delayed links, TOML graph loading, preparation, deterministic model-time drivers, and the lockstep HIL boundary. Scientific modules retain their numerical implementations and domain APIs. |
| Array backend | A semantic array/provider family such as CPU, CUDA, or AMDGPU. It is not a particular accelerator device. |
| Compute device | The concrete host or accelerator that owns an array and executes a prepared operation. A compute device is not an optical component or a graph node. |
| Preparation | The cold phase that validates configuration and binds concrete plans, state, workspaces, products, backend, device, and exact input/output storage before repeated execution. |
| Plan | A run-immutable numerical or physical execution contract. Persistent scientific state, replaceable scratch, products, and exact external bindings are not plan data. |
| State | Mutable values that affect later scientific results, such as atmosphere evolution, controller history, detector persistence, delayed graph values, or RNG state. State has one execution writer. |
| Workspace | Replaceable mutable scratch and execution resources. Recreating a workspace must not change the intended scientific trajectory. |
| Product | A caller-visible scientific result such as a pupil function, intensity map, WFS observation, WFS measurement, detector frame, or named graph output. Products are not scratch. |
| Prepared execution owner | The concrete owner that binds one plan, state, workspace, products, exact arrays, backend/device/context, and single-writer execution contract. |
| Algorithm graph | A finite static composition of prepared AOS-native nodes connected by validated named ports. Version 1 is single-rate and publishes complete frames. |
| Algorithm node | A graph adapter around one scientific operation. Its configuration, port contracts, preparation, step, and reset methods are separate from the underlying domain algorithm. |
| Direct link | A same-frame connection from one node output to a later node input in topological order. |
| Delayed link | A connection that presents the previous completed frame's value and therefore breaks a feedback cycle explicitly. |
| Graph input | Caller-owned storage admitted as an external input to a prepared graph. |
| Graph output | Caller-visible storage published after a successful complete graph step. |
| Model timestamp | `AlgorithmGraphs.ModelTimestamp`: an exact nonnegative integer nanosecond coordinate used for model ordering. It is not a wall-clock reading. |
| Model duration | `AlgorithmGraphs.ModelDuration`: an exact nonnegative integer nanosecond interval. |
| Periodic schedule | `AlgorithmGraphs.PeriodicSchedule`: a positive exact period plus phase that maps a positive sequence to a model timestamp. |
| Complete frame | One atomically published detector or graph product after all operations required for that frame have succeeded. Row groups or intermediate optical samples are not partial published frames. |
| Single writer | Exactly one prepared execution owner may mutate a state or output during execution. This is an ownership rule, not a prohibition on multiple sources, DMs, guide stars, optical branches, or coarse parallelism across independent owners. |
| Prepared graph HIL boundary | `PreparedGraphHILBoundary`: one transport-neutral lockstep exchange between a prepared graph's complete detector frame and a complete host command. It owns sequence/failure state and host exchange buffers, but no socket, PipeWire node, wall-clock pacer, or RTC protocol. |
| HIL reference system | A fully declared, non-instrument AO plant used to validate complete-frame exchange with an external RTC. Its aperture, deformable-mirror command coordinates and influence model, uncompensated OPD input, WFS optics, detector response, command units, and deterministic calibration policy are all controlled inputs. It may preserve the topology of an instrument workflow, but it is not a REVOLT profile, measured instrument model, RTC implementation, or scientific reference dataset. |
| Frame sequence | The positive graph-step sequence attached to a completed HIL frame. The boundary requires a same-sequence command response before the next frame. |
| HIL execution time | Host-side time at which simulation work runs. It is distinct from exact model time and from a detector or RTC's reported timestamp domain. |
| Rolling shutter | A detector exposure in which rows or row groups integrate at different model times. The optical path may be reevaluated at those times while the detector publishes one complete frame. |
| Proper prescription | A Proper.jl propagation function plus prepared application-owned context. It enters AdaptiveOpticsSim through explicit optical products or a graph-node adapter; Proper remains optional. |
| NGS | Natural guide star. |
| LGS | Laser guide star. |
| MCAO | Multi-conjugate adaptive optics, normally with several guide stars and DMs at distinct conjugate altitudes. |
| MOAO | Multi-object adaptive optics, with target-specific correction paths in addition to shared sensing or tomography. |
| RTC | Real-time controller. In HIL use the RTC consumes simulated sensor frames and returns complete commands; AdaptiveOpticsSim does not need to simulate the RTC unless a graph intentionally includes controller nodes. |
| HIL | Hardware-in-the-loop execution connecting simulated optical/sensor products to external hardware or RTC software through an explicit boundary. |

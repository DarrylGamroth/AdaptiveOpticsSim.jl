# Project Glossary

Status: active

This is the canonical terminology guide for public APIs, implementation names,
documentation, requirements, and tests. Plane names describe optical location;
product names describe the represented quantity. New scientific terms should be
defined here before they become public API.

## Naming Rules

- Do not combine a plane location and an assumed physical quantity in one type
  name. Use, for example, an `IntensityMap` whose metadata says `FocalPlane()`.
- State coordinate domain and units explicitly. Do not infer metres or radians
  from plane kind alone.
- Use *rate*, *exposure*, and *count* according to whether time has not yet been
  integrated, has been integrated per area, or has been integrated per sample.
- Use *MTF* only for a frequency-domain modulation transfer function. A kernel
  applied to an image is a spatial-domain response model.
- Use *WFS signal* for a sensor-independent typed measurement. Use *slope* only
  when the values are wavefront gradients or calibrated centroid-equivalent
  slopes.

Package-architecture terms are used consistently as follows:

| Term | Project meaning |
|---|---|
| Canonical owner | The one Julia module that defines and maintains a supported binding or generic-function identity. Other modules import that identity and add methods where appropriate; they do not create parallel generics or root forwarding aliases. |
| API allowlist | The exact exported and qualified-`public` bindings maintained by one canonical owner. An allowlist is an equality contract, not a maximum-size budget or a representative sample. |
| Extension hook | A generic function intentionally extended by an optional package extension. The hook retains one canonical owner even when methods are supplied for several optional dependencies. |
| Cross-module import | An explicit import of a binding from its canonical owner for package-internal composition. It does not transfer ownership or make the binding public. |
| Definition | Cold, reusable configuration from which a run is prepared. A definition contains no prepared arrays, mutable run state, scratch, exact product binding, schedule, queue, or transport owner. |
| Execution plan | A run-immutable numerical or physical contract produced or validated during preparation. A plan may retain dimensions, mappings, coefficients, backend/device requirements, and a logically immutable reentrant operator, but not persistent scientific state, replaceable scratch, caller-visible products, or incidental exact-array identity. A type uses the `Plan` suffix only when it satisfies this contract. |
| Execution strategy | An immutable dispatch choice that selects how an operation is performed but does not own a prepared numerical contract. Use `Strategy`, `ExecutionStyle`, or a more specific accepted term rather than `Plan`. |
| Execution state | Persistent mutable values whose contents can affect a later scientific result. State has one writer and explicit reset, checkpoint, or replay semantics where those operations are supported. If discarding a value can change the next result, it is state rather than workspace. |
| Execution workspace | Replaceable scratch or execution resources used by a prepared operation. Recreating a workspace cannot change the deterministic physical trajectory. A stream-bound, task-bound, scratch-owning, or non-reentrant backend handle is workspace or prepared-owner state, not automatically part of a plan. |
| Product | A caller-visible scientific or integration result with explicit ownership and metadata. A product is not workspace merely because a mutating execution method writes it. |
| Prepared execution owner | A single-writer run owner that binds exact plan, state, workspace, input, output, and backend/device/context identities and validates those bindings before repeated mutation. A prepared owner may provide a convenient routine API, but it is not itself an algorithm plan solely because it was constructed during preparation. |
| Bounded prepared storage | Storage allocated to its admitted final capacity during preparation and unavailable for growth while armed. Boundedness is an owner and lifecycle invariant, not a property inferred from a low-level container type. Package code does not directly use Julia's `Memory`. Homogeneous armed host storage uses [FixedSizeArrays.jl](https://github.com/JuliaArrays/FixedSizeArrays.jl)'s `FixedSizeArray` with a concrete element type; a `Vector` may be used only as a cold builder before sealing. Heterogeneous storage uses tuples, concrete unions, family-grouped or purpose-built owners, while numerical device storage uses its native backend arrays. `FixedSizeArray` may encapsulate `Memory` internally on supported Julia versions; package code depends on the fixed-size array contract rather than that backing type. |
| Type-erased storage | A struct field or collection whose stored type is `Any`, an abstract type, or an uninstantiated parametric family. `Any`-typed storage is boxed and prevents the owner from expressing a concrete execution contract. It does not become suitable by changing its container; bounded heterogeneous execution requires concrete family groups, tuple/union/owner storage, or an explicit prepared function barrier with allocation and inference evidence. An unconstrained `::Any`, `<:Any`, or `Vararg{Any}` method signature is a dispatch wildcard rather than stored representation and is reviewed separately. |

## Optical Planes, Coordinates, And Products

| Term | Project meaning |
|---|---|
| Pupil plane | A transverse plane conjugate to the aperture stop. Represented by `PupilPlane()`. |
| Focal plane | A physical focus or focal-mask plane. Represented by `FocalPlane()`. Its coordinates may be angular when that is the declared propagation output. |
| Pupil-plane placement | `Plant.PupilPlanePlacement()`: the declared optical location of a component in a plane conjugate to the aperture stop. It is optical placement, not CPU/GPU placement, command cadence, or controller grouping. |
| Atmospheric-conjugate placement | `Plant.AtmosphericConjugatePlacement(altitude_m)`: a geometric component plane conjugate to a finite nonnegative altitude above the entrance pupil, expressed in metres. The altitude declares the geometric source-footprint transform; by itself it is not a diffractive relay prescription. |
| Focal-plane placement | `Plant.FocalPlanePlacement()`: the declared location of a component at a physical focus or focal-mask plane. The current native executable use is the path-local autonomous Pyramid modulator. |
| Path visibility | An immutable declaration of which optical paths contain a component. `Plant.AllPathVisibility()` selects every declared path; `Plant.SelectedPathVisibility(...)` selects an explicit nonempty set of `OpticalPathID` values. Visibility does not imply cadence, controller grouping, or execution-resource placement. |
| Source footprint | The pupil-domain region and coordinate mapping intercepted by a source ray bundle at a declared conjugate altitude. It depends on source direction and, for a finite-height LGS, cone scaling, then on any explicitly declared pupil-relay registration. Declaring a conjugate altitude does not itself implement this transform. |
| Pupil-relay registration | `Plant.PupilRelayRegistration`: the cold affine registration from geometric source-footprint coordinates to one sampled pupil-surface grid. It declares positive per-axis pupil magnification, counterclockwise rotation, per-axis parity, and a metric decenter in that order; sampled-plane origin, sampling, axis order, and axis signs remain properties of `OpticalPlaneMetadata`. This registration is path/relay geometry. It is distinct from `Misregistration`, which acts inside DM surface formation by registering actuator coordinates to the sampled DM surface and must not be applied again during path coupling. |
| Prepared pupil-footprint coupling | An immutable path-local mapping from one exact prepared pupil input to a compatible sampled pupil-surface grid. `Plant.PreparedIdentityPupilFootprintCoupling` is the same-grid fast path; `Plant.PreparedPupilFootprintCoupling` stores the finite-support affine sample mapping for a particular source direction and conjugate altitude. Neither value owns command state, surface state, cadence, or transport. |
| Image plane | An image-forming plane. Use this term in prose when the distinction from a focal-mask plane matters; introduce a concrete marker only with an implemented contract. |
| Detector plane | The optical sampling plane incident on a detector, represented by `DetectorPlane()`. It is not the detector readout frame itself. |
| Intermediate plane | A known transverse optical plane that is not more specifically a pupil, focal, image, or detector plane. Represented by `IntermediatePlane()`; do not use *propagation plane*. |
| Metric coordinates | Plane `sampling` and `origin` are in metres. Represented by `MetricCoordinates()`. |
| Angular coordinates | Plane `sampling` and `origin` are in radians. Represented by `AngularCoordinates()`. |
| Normalized pupil coordinates | Dimensionless coordinates normalized to the entrance-pupil diameter, represented by `NormalizedPupilCoordinates()`. For a re-imaged-pupil detector mosaic they describe the optical relay sampling, not a manufactured detector's physical pixel pitch. |
| Sample-centered | A geometric origin lies on a stored sample. |
| Inter-sample-centered | A geometric origin lies between stored samples. This is not necessarily an inter-pixel convention. |
| Telescope definition | `Optics.TelescopeDefinition`: an immutable, configuration-only declaration of the currently supported annular telescope aperture. It contains scalar aperture geometry, scalar pupil reflectivity, numeric type, and an explicit revision, but no sampled arrays, mutable state, array backend, or compute device. `prepare_telescope(definition, target)` materializes its numerical `Telescope` on one exact compute device. |
| Telescope aperture | The revisioned support, intensity reflectivity, diameter, and spatial sampling prepared by `TelescopeAperture`. It is geometry shared while paths are prepared; it is not a mutable wavefront or OPD buffer. |
| Pupil function | The complex pupil transmission in Fourier optics. `PupilFunction` snapshots one telescope-aperture revision, stores its wavelength-independent support and field amplitude, and owns the mutable OPD for one path; field formation realizes the wavelength-specific complex pupil. |
| Pupil reflectivity | The finite dimensionless intensity-throughput fraction in `[0, 1]` stored by `TelescopeAperture`. Optical field formation applies its square root as an amplitude transmission. It is not an amplitude coefficient itself. |
| Electric field | In this package, a scalar complex optical field envelope/phasor sampled on a declared plane. `ElectricField` is not an SI vector electromagnetic field in V/m unless its metadata explicitly establishes such a normalization. |
| Intensity | The computational quantity `abs2(E)`. Its physical units and normalization follow the field and metadata; the word alone does not assert radiometric irradiance. |
| Intensity map | A real sampled array of intensity values plus `OpticalPlaneMetadata`, represented by `IntensityMap`. The metadata, not the type name, states plane location and physical semantics. |
| Photon-arrival-rate intensity map | An `IntensityMap` with `PhotonRateNormalization()` and an explicit spatial measure. It represents a rate before detector exposure: either a spatial density or a rate integrated over each represented cell. |
| Direct imaging | Native image formation from a declared pupil function or preformed pupil-plane electric field to a caller-owned focal-plane photon-arrival-rate `IntensityMap`. `prepare_direct_imaging` fixes storage, grid, backend, device, and workspace; `form_direct_image!` executes without applying detector exposure time. The current off-axis model resolves a finite integer displacement during preparation, honors the focal grid's declared `:x`/`:y` axis order and signs, and applies a periodic shift. |
| Direct-imaging batch | A prepared native Fraunhofer execution group for an ordered set of compatible physical direct-science source samples. It owns one stacked field workspace, one stacked photon-arrival-rate allocation, and one FFT plan over the two optical axes while exposing each sample as an ordinary focal-plane `IntensityMap` view in an `OpticalProductBundle`. Direction and wavelength remain sample metadata; the batch performs no coherent source combination, spectral integration, detector exposure, implicit resampling, host transfer, or runtime regrouping. |
| Optical path difference (OPD) | Scalar optical path-length difference in metres. Positive-sign convention must be validated at integration boundaries. |
| Sampled aberration | A fixed sampled OPD perturbation declared with `Plant.SampledAberrationDefinition`. It carries stable identity, exact `OpticalPlaneMetadata`, optical placement, path visibility, additive or replacement application, and optional pupil-relay registration. Plant preparation copies its native `NCPA` or `OPDMap` storage onto the prepared plant's exact compute device and binds it to exact path-local pupil-footprint couplings. Caller-owned host samples are preparation inputs; a direct copy from one accelerator to a different accelerator is rejected. It is not a controllable device or a cadence-bearing state owner. |
| Point-spread function (PSF) | The image-plane response to a point source under an explicitly declared normalization. A source-brightness- and exposure-scaled image is not intrinsically a PSF. |
| Non-common-path aberration (NCPA) | Aberration visible to one optical branch but not to its reference or sensing branch. `Optics.NCPA` is the physical sampled OPD map in metres; KL/Zernike/M2C basis selection and coefficient generation are calibration policy, and path visibility is a Plant concern. Model the resulting optic in the branch where it physically occurs. |

`UnspecifiedSpectralCoordinate()` means that no spectral coordinate has yet been
declared; it does not mean wavelength independence.
`AchromaticSpectralCoordinate()` explicitly declares wavelength-independent
geometry or data. `MonochromaticChannel(λ)` declares one wavelength in metres.
`IntegratedSpectralChannel(id)` declares that values have already been integrated
over an application-defined passband identified by `id`; equal identifiers are
the compatibility contract, while the passband definition remains application
owned.

## Radiometry And Photon Quantities

| Term | Unit and use |
|---|---|
| Radiant irradiance | Incident radiant flux density, W·m⁻². Use *irradiance* without a photon qualifier only when this radiometric meaning is intended. |
| Photon irradiance | Incident photon-rate density, photons·s⁻¹·m⁻². `photon_irradiance(source)` uses this quantity. |
| Spectral sample weight | The normalized photon-number fraction of `photon_irradiance(source)` assigned to one `SpectralSample` in a `SpectralBundle`. It is not a radiant-energy fraction. Ordinary bundle constructors normalize nonnegative proportional input weights to sum to one. |
| Photon flux | Photon rate, photons·s⁻¹, integrated over a stated receiving area or channel. Do not use it for a per-area source value. |
| Photon-arrival-rate product | Detector-facing umbrella term when metadata may declare either a spatial density or a cell-integrated photon rate. |
| Photon exposure | Time-integrated photon irradiance, photons·m⁻². |
| Expected photon count | Expected photons integrated over both time and represented cell area. It is the mean supplied to photon-counting statistics. |
| Relative or normalized intensity | Dimensionless intensity under a declared normalization, such as unit total power, peak, or contrast. It cannot enter a physical detector acquisition without an explicit scaling contract. |
| Point-sampled measure | `PointSampledMeasure()`: each value is evaluated at a coordinate and includes no represented cell area. It cannot enter detector acquisition without an explicit spatial mapping or integration. |
| Spatial-density measure | `SpatialDensityMeasure()`: each value is per unit area of the declared coordinate domain. Detector acquisition multiplies it by the represented cell area before exposure integration. A photon-rate density on metric coordinates is photon irradiance. |
| Cell-integrated measure | `CellIntegratedMeasure()`: each value has already been integrated over its represented spatial cell. A photon-rate-normalized value therefore has units photons·s⁻¹ per cell. |
| Coherent field combination | `CoherentFieldCombination()`: compatible complex fields may be combined before intensity formation, so relative phase is retained. |
| Incoherent intensity addition | `IncoherentIntensityAddition()`: compatible intensity maps may be added elementwise after their grid, spectral, radiometric, backend, and device contracts have been checked. |
| Non-combinable product | `NonCombinableProduct()`: the product must remain separate unless an explicit physically justified mapping is prepared. |
| Optical product bundle | `OpticalProductBundle`: a typed, fixed-cardinality collection that preserves products on incompatible grids or channels without implicit resampling, radiometric conversion, or accumulation. Its container cannot grow or shrink; a prepared execution owner independently binds the exact ordered members and rejects replacement before numerical mutation. Each leaf's caller-owned numerical array remains mutable. |
| Normalized test source | A source carrying `NormalizedTestSource()` radiometry and dimensionless relative power. It is useful for calibration and deterministic tests, but does not claim physical photon irradiance and requires an explicit scale before physical detector acquisition. |

The detector boundary distinguishes photon-rate density from cell-integrated
photon rate. The WFS optics stage applies no elapsed-time factor. A prepared
detector acquisition validates the map metadata, applies the presampling
response before physical-pixel integration, and integrates its explicit
exposure duration exactly once. Incompatible maps remain separate in an
`OpticalProductBundle` unless an explicit conversion is prepared.

The definitions of [irradiance](https://cie.co.at/eilvterm/17-21-053),
[photon irradiance](https://cie.co.at/eilvterm/17-21-058),
[photon flux](https://cie.co.at/eilvterm/17-21-040), and
[photon exposure](https://cie.co.at/eilvterm/17-21-073) follow the CIE
International Lighting Vocabulary.

## Detector Response

| Term | Project meaning |
|---|---|
| Presampling detector response | A spatial-domain response applied before discrete detector sampling or binning. `GaussianPixelResponse`, `SampledFrameResponse`, and `RectangularPixelAperture` are response models. A sampled kernel is a centered discrete impulse response: its positive row and column offsets appear at the same offsets from an input impulse. |
| Detector acquisition plan | `Detectors.DetectorAcquisitionPlan`: the run-immutable numerical and radiometric contract for one compatible frame-detector configuration and immutable `IntensityMap` description. It owns detector parameters, input metadata and shapes, output shapes, photon-rate scaling, and declared-channel QE. It owns no live detector, mutable input storage, persistent detector state, workspace, or product. |
| Detector acquisition state | Persistent mutable detector values that can affect a later scientific result: accumulated charge, persistence state, thermal state, integrated duration, and readiness where applicable. State has one writer and is not replaceable scratch. |
| Detector acquisition workspace | Replaceable scratch and execution resources used by detector response, physical-pixel integration, temporal sampling, stochastic response, host staging, and readout fitting. Recreating compatible workspace cannot change a deterministic trajectory. |
| Detector acquisition products | Caller-visible detector results, including the integrated frame, converted output, and configured readout products. Readout cubes, fit values, and read times are products; intermediate averages and full-frame fitting arrays are workspace. A kernel may write directly into a product without making that product scratch. |
| Prepared detector acquisition | `Detectors.PreparedDetectorAcquisition`: the exact single-writer binding of one frame detector, one mutable `IntensityMap` storage identity, its detector acquisition plan, persistent state, replaceable workspace, and caller-visible products. `prepare_detector_acquisition` validates current finite nonnegative input samples, plane, radiometry, spatial measure, declared-channel QE, shapes, backend, compute device, and forbidden aliases before publishing the owner. Repeated `capture!` trusts later producer writes to the bound input storage; replacing a bound owner requires preparation again. |
| Event-driven detector acquisition | A prepared virtual-time lifecycle over one exact prepared detector acquisition. Global-shutter, rolling-shutter, and frame-transfer definitions retain immutable timing; their prepared lifecycles bind that acquisition, grant exactly one separately owned mutable lifecycle state, and use fixed-cardinality `FixedSizeVector` read-offset schedules. Begin, half-open interval accumulation, row-band transition or nondestructive read, close or image-to-storage transfer, readout completion, and readiness are explicit transitions where applicable. |
| Half-open exposure | An exposure interval `[start, close)`: optical samples at `start` are included, while a sample timestamped exactly at `close` is excluded. Integer `PlantTimestamp` boundaries, rather than floating accumulated-time tolerance, determine membership and completion. |
| Integration duration | The positive duration in seconds over which one detector-facing photon-arrival-rate sample contributes to an exposure. The current incremental convenience API names this `integration_duration`; it is neither an absolute sample timestamp nor the sample period between consecutive samples. A virtual-time scheduler owns the interval boundaries. |
| Nondestructive read | A detector read that observes accumulated charge without ending or resetting the active integration. A scheduled up-the-ramp model records the charge state at each declared read event; a post-exposure cube synthesized from one final frame is a lower-fidelity convenience, not a time-resolved nondestructive-read simulation. |
| Skipper CCD sample duration | `CCDSensor.sample_duration`: the elapsed duration assigned to one configured full-frame nondestructive sample in `SkipperSampling`. Total sampling duration is the product of this duration and the fixed sample count. It is not a sample period, a whole conventional-CCD readout duration, or a model of the correlated-double-sampling electronics integration window. |
| InGaAs area sensor | An area detector using indium gallium arsenide photosensitive material. `InGaAsSensor` supplies product-neutral glow and optional frame-to-frame persistence behavior while the owning `Detector` supplies dark current, QE, defects, nonlinearity, saturation, gain, and any explicit presampling response. The technology name does not imply a wavelength response, pixel aperture, blur, MTF, IPC, readout mode, or camera profile. |
| Frame-to-frame exponential persistence | `ExponentialPersistence(coupling, decay)`: a discrete latent-signal recurrence. For the sensor-defined frame \\(q_k\\) and latent state \\(l_k\\), \\(l_{k+1}=\\mathrm{decay}\\,l_k+\\mathrm{coupling}\\,q_k\\); \\(l_k\\) is added to the next frame. The dimensionless coefficients apply once per completed frame. They do not define an elapsed-time constant, exposure scaling, trap population, calibrated detector persistence, or a universal pipeline boundary. For `InGaAsSensor`, \\(q_k\\) is specifically the post-nonlinearity, post-saturation, post-charge-coupling frame before read noise, conversion gain, correction, quantization, and background subtraction. |
| Conventional HgCdTe array | An area detector using mercury-cadmium-telluride photosensitive material without avalanche multiplication in the modeled signal path. `HgCdTeSensor` composes the product-neutral `HgCdTeReadout` configuration for single, averaged nondestructive, correlated-double, Fowler, or up-the-ramp sampling. |
| HgCdTe linear-avalanche photodiode array | An HgCdTe area detector operated with linear avalanche multiplication. `HgCdTeAvalancheArraySensor` adds explicit avalanche gain, an excess-noise factor, and a multiplication model to the shared HgCdTe readout contract; it is distinct from a Geiger-mode SPAD/counting detector. |
| Linear-mode APD channel detector | `LinearAPDDetector`: one analog avalanche-photodiode element or a fixed bank of independent channels. `SingleElementLinearAPD` accepts scalar or one-element-vector photon flux; `LinearAPDChannelBank(n)` accepts exactly `n` photon-flux channels. Storage and output are one-dimensional and do not imply pixels or an area frame. This regime is distinct from Geiger-mode SPAD counting. |
| SPAD accumulated-count array | `SPADArrayDetector((rows, columns); ...)`: a fixed-shape area detector whose input is an already cell-integrated photon-arrival rate. It produces one accumulated expected-count or sampled-count image per integration. It is not a photon-event stream and does not model avalanche timestamps, energy, time-over-threshold, or per-event correlations. |
| Active-area detection efficiency | `SPADArraySensor.active_area_detection_efficiency`: the expected fraction of photons incident on the photosensitive area that trigger accepted detections before dead-time loss. The separately declared fill factor scales the geometrical active fraction once. Neither scalar implies a wavelength curve or a pixel-aperture MTF. |
| MKID accumulated-count array | `MKIDArrayDetector`: an area detector whose matrix input is an already cell-integrated, spectrally prefiltered photon-arrival rate. It produces one accumulated expected-count or sampled-count image per integration. It does not produce photon-arrival timestamps or per-photon energy estimates. Optional physical characteristics belong to `MKIDArrayCharacteristics` and do not change that observable boundary. |
| Energy resolving power | `MKIDArrayCharacteristics.energy_resolving_power`: the optional dimensionless physical characteristic \(R=E/\Delta E\). It is detector metadata, not an energy estimate and not evidence that the accumulated-count image resolves individual photon energies. |
| Photon-arrival-time resolution | `MKIDArrayCharacteristics.photon_arrival_time_resolution_s`: an optional positive detector characteristic in seconds. It is not a simulated timestamp, trigger jitter, integration duration, or sample period. |
| MKID wavelength passband | `MKIDArrayCharacteristics.wavelength_passband_m`: an optional inclusive `(minimum, maximum)` source-wavelength interval in meters. Source-aware capture filters scalar and weighted spectral sources against it. Matrix-only capture assumes the producer already applied spectral filtering. This scalar passband is not a calibrated wavelength-dependent QE curve. |
| Counting dead-time mean response | A deterministic map from the pre-dead-time expected count per live integration to its post-dead-time expectation. `NonParalyzableDeadTime` uses \(\mu/(1+\mu\tau/t_\mathrm{live})\); `ParalyzableDeadTime` uses \(\mu\exp(-\mu\tau/t_\mathrm{live})\). The optional Poisson stage samples the resulting expectation and is an explicitly lower-order surrogate for the true non-Poisson dead-time count distribution. |
| First-order afterpulse mean response | `FirstOrderAfterpulseMeanResponse(a)`: a deterministic accumulated-count approximation that multiplies the expected detections by \(1+a\), where `a` is the nonnegative mean number of first-order afterpulse counts per detection. It does not simulate avalanche history, afterpulse delay, higher generations, or the resulting overdispersed count statistics. |
| Nearest-neighbor count redistribution | `NearestNeighborCountRedistribution(f)`: a deterministic, count-conserving image operation that retains fraction \(1-f\) in each source cell and divides fraction \(f\) across that source cell's orthogonal in-bounds neighbors. It is an explicit reduced response, not a claim of optical blur, electrical crosstalk, SPAD avalanche propagation, or detector MTF. |
| Avalanche excess-noise factor | For one input carrier with stochastic multiplication \(M\), the dimensionless factor \(F=\mathrm{E}[M^2]/\mathrm{E}[M]^2=1+\mathrm{Var}(M)/\mathrm{E}[M]^2\). For input charge \(q\) whose carriers multiply independently, the implemented input-referred multiplication variance is \((F-1)q\), before multiplication by the square of the mean avalanche gain. This detector-literature definition is used by the linear-mode APD and HgCdTe avalanche models; it is not the EMCCD API's input-referred standard-deviation factor. |
| Conditional-Gamma avalanche multiplication | `Detectors.ConditionalGammaAvalancheMultiplication`: a nonnegative CPU reference model in which input-referred multiplied charge conditional on \(q>0\) is Gamma distributed with shape \(q/(F-1)\) and scale \(F-1\); \(F=1\) is deterministic. It models independent multiplication of input carriers and is not a photon-counting or timestamp model. |
| Clipped-Gaussian avalanche multiplication approximation | `Detectors.ClippedGaussianAvalancheMultiplicationApproximation`: a backend-portable approximation to conditional avalanche multiplication, \(q'=\max(q+\sqrt{(F-1)q}Z,0)\) for standard-normal \(Z\). Qualification is restricted to the moderate-charge regime \(q/(F-1)\geq25\), where truncation is negligible; lower-charge output is computationally defined but not claimed as a faithful multiplication distribution. |
| Synthesized final-charge ramp | The lower-fidelity direct-`capture!` up-the-ramp product labeled `:synthesized_final_charge`. It scales one completed charge realization to evenly spaced read times before fitting and cannot represent intra-exposure optical changes. |
| Scheduled evolving-charge ramp | The Plant event product labeled `:scheduled_evolving_charge`. Each nondestructive-read event snapshots charge accumulated through its actual prepared timestamp, including nanosecond-quantized irregular spacing. |
| Rolling-shutter row band | One contiguous prepared group of detector rows sharing open and close timestamps. `RollingShutterAcquisitionState` retains only bounded opened- and closed-band cursors. In rolling exposure, bands open and close in sequence with equal nominal exposure; in global reset exposure, every band opens together and later bands close later. |
| Frame output window | `FrameWindow`: the rectangular region copied from a completed full detector frame into the reusable output product. It does not change exposed sensor geometry, row-band timestamps, or acquisition duration. Model a physically cropped sensor region with the corresponding detector frame dimensions. |
| CMOS shared row and column noise | Independent zero-mean Gaussian readout offsets drawn once per row or once per column for each completed frame, then shared by every pixel in that row or column. Their spatial covariance differs from both uniform independent read noise and the heteroscedastic independent `CMOSReadNoiseMap`; temporally correlated 1/f and random-telegraph noise are separate, unimplemented models. |
| Frame-transfer storage area | The light-shielded detector storage region that receives a completed EMCCD image-area exposure before serial readout. `PreparedFrameTransferAcquisition` models one non-aliasing storage-frame capacity, allowing the image area to integrate the next frame while that storage frame is read. It changes acquisition timing, not optical response or detector MTF. |
| Readout completion / product readiness / acquisition readiness | Readout completion finalizes a complete detector product at its declared plant timestamp. Product readiness records when that complete product is available to its caller-owned destination. Acquisition readiness is the distinct transition that permits another exposure. A frame-transfer image area may already be integrating while the preceding storage product completes readout; a non-frame-transfer detector may remain unrearmed after product completion when a readiness delay is configured. |
| Pixel aperture | The photosensitive spatial support and fill factor of one pixel. `RectangularPixelAperture` is separable in the implemented rectangular case, but its detector-grid kernel does not claim continuous subpixel geometry; that requires an explicit oversampled optical-grid mapping. |
| Optical transfer function (OTF) | The complex spatial-frequency response associated with an imaging response. |
| Modulation transfer function (MTF) | The magnitude of the OTF. `detector_mtf` is the normalized interior, infinite-grid transfer magnitude of the realized discrete response kernel, in cycles per detector pixel. A finite detector uses zero extension and therefore has boundary-dependent response rather than one global MTF. The diagnostic does not claim the continuous subpixel-aperture MTF; that requires an explicit oversampled optical-grid mapping. No spatial kernel type is itself named an MTF. |
| Quantum efficiency (QE) | Expected collected signal carriers per incident photon under the declared spectral model. |
| PRNU / DSNU | Pixel-response nonuniformity / dark-signal nonuniformity. |
| Clock-induced charge (CIC) | Spurious charge generated by detector clocking. `clock_induced_charge_per_frame` is the implemented independent Poisson expectation in electrons per pixel per completed frame; it is not a per-second rate and is not scaled by exposure duration. |
| EMCCD excess-noise factor | The input-referred factor \(F \ge 1\) by which stochastic electron multiplication increases the shot-plus-background variance in linear operation. The conditional multiplication variance factor used by the implemented models is \(\sqrt{F^2-1}\), optionally bounded below by the model's declared minimum factor. |
| Conditional-Gamma multiplication | The CPU-only `ConditionalGammaMultiplication` model: for input charge \(q>0\), effective conditional factor \(f>0\), and mean gain \(g\), output is Gamma-distributed with shape \(q/f^2\) and scale \(g f^2\). Zero factor is deterministic gain. This is a conditional high-gain multiplication model, not a stage-by-stage register simulation. |
| Clipped-Gaussian multiplication approximation | The backend-portable `ClippedGaussianMultiplicationApproximation`: conditional output is \(g\max(q + f\sqrt{q}Z, 0)\) for standard-normal \(Z\). It is a nonnegative moment approximation intended for moderate-to-high charge, not the conditional-Gamma distribution and not a low-charge photon-event model. |
| EMCCD photon-counting output | A binary, coincidence-limited frame produced by thresholding the post-multiplication/read-noise value and then applying the configured Bernoulli detection efficiency. Multiple accepted photoelectrons in one pixel and frame still produce one output event. |
| Interpixel capacitance (IPC) | Post-collection capacitive charge coupling between detector nodes, not a presampling optical blur. |

CCD, EMCCD, CMOS, sCMOS, quantitative low-noise CMOS, InGaAs, conventional
HgCdTe, HgCdTe linear-avalanche photodiode arrays, Skipper CCD, SPAD, MKID, and linear-mode APD
describe detector technology or readout families. Configured CMOS variants
share the CMOS architecture in core; named commercial camera profiles belong
in a companion package. A single-element linear-mode APD is a channel detector and is not
forced into an area-frame API.

## WFS And HIL Terms

| Term | Project meaning |
|---|---|
| Backends namespace | `AdaptiveOpticsSim.Backends`: the canonical Julia owner of semantic array-backend selectors, concrete compute-device identity, and backend extension protocols for allocation, FFTs, reductions, random generation, kernel execution, and synchronization. It owns numerical execution mechanics, not physical model kernels, task scheduling, or CPU/GPU placement policy. `AdaptiveOpticsSim` exports the module itself but does not provide root compatibility bindings for its contents. |
| Optics namespace | `AdaptiveOpticsSim.Optics`: the implemented canonical Julia owner of apertures, telescopes, sources, optical-plane metadata and products, pupil and electric-field formation, general propagation, direct imaging, sampled OPD, physical NCPA, controllable optics, and reusable physical WFS components. Atmosphere-coupled propagation, detector response, composed WFS estimation, calibration synthesis, and plant visibility or scheduling belong to their respective owners. |
| Array backend | A semantic software/provider family selected by `Backends.CPUBackend()`, `Backends.CUDABackend()`, `Backends.AMDGPUBackend()`, or `Backends.MetalBackend()`. It determines compatible array construction and numerical dispatch, but it does not identify one concrete accelerator when a process can address several devices in the same family. |
| Compute device | The concrete host or accelerator on which array storage resides and prepared numerical work executes, represented by `Backends.HostComputeDevice` or a family-qualified `Backends.AcceleratorComputeDevice`. `Backends.compute_device(array)` reports this run-local identity; supported array views report their parent's identity. A compute device is distinct from an AO component being simulated, an optical-plane location, a worker/task, and an HIL execution resource. A backend runtime's device ordinal is sufficient for same-process compatibility but is not a stable declared plant identity. |
| Exact compute-device availability | A cold, run-local result reporting whether the owning backend runtime can currently select one requested `Backends.AbstractComputeDevice`. `Backends.compute_device_availability` returns either `ComputeDeviceAvailable` or `ComputeDeviceUnavailable` with a structured reason. Availability does not prove that a particular plant model supports the device, that memory admission succeeds, or that the placement meets a deadline. |
| Placement namespace | `AdaptiveOpticsHIL.Placement`: the qualified owner of immutable, transport-neutral input values for static HIL execution-resource placement. Its caller-supplied facts and policies do not discover hardware, select or admit a plan, allocate handoff storage, bind an Agent owner, or change run lifecycle state. |
| Execution resource | `Placement.ExecutionResource`: one stable HIL inventory record to which a complete prepared execution group may be assigned. It identifies one exact Core compute device together with its memory domain, CPU worker/NUMA facts or accelerator context, capacities, and reserved coordination contexts needed by placement; it is not synonymous with that compute device. It is not an optical component, a path-group ordinal, an Agent execution-owner ID, or a Julia task. |
| Memory domain | One explicitly identified storage and transfer-coherence domain in an HIL resource inventory, such as host memory associated with a CPU/NUMA placement or memory owned by one accelerator. Sharing an array-backend family does not imply the same memory domain. Movement between domains is an explicit prepared handoff, not an ordinary hidden copy. |
| Resource inventory | `Placement.ResourceInventory`: an immutable, canonically ordered snapshot of `Placement.ExecutionResource` values and their reserved coordination contexts. Its exact common `Placement.FactProvenance` records the caller-supplied capability snapshot source; it does not discover or reserve hardware. |
| Placement fact provenance and version | `Placement.FactProvenance` is the immutable source identity and `Placement.PlacementFactVersion` is the positive version of one caller-supplied placement-fact snapshot. A changed source procedure or fact revision requires a distinct provenance; provenance is not a planner version, plan admission, or runtime observation. |
| Placement byte count | `Placement.KnownByteCount` is a nonnegative byte quantity supplied by the caller; `Placement.UnknownByteCount` explicitly represents a quantity that the caller has not measured or derived. Unknown never means zero bytes, and byte-count facts do not infer capacity from an accelerator object. |
| Target-capability snapshot | `Placement.CapabilitySnapshot` is a defensively snapshotted, versioned set of named `Placement.TargetCapability` results for one target. Each availability is explicitly `CapabilitySupported`, `CapabilityUnsupported`, or `CapabilityUnknown`; unknown never means supported. |
| Placement subject | The exact thing to which a placement fact or policy applies: `Placement.PathExecutionGroupSubject` for one complete path and acquisition group, `Placement.AtmosphereAuthoritySubject` or `Placement.CommandAuthoritySubject` for the unique authority, or `Placement.AcquisitionOutputSubject` for a complete group's output disposition. A subject is not an execution resource, compute device, execution owner, or individual kernel/task. |
| Placement resource estimate | `Placement.ResourceEstimate`: a provenance-bearing estimate of resident and workspace `Placement` byte counts for one placement subject on one candidate execution resource. It is a planning input, not admitted storage, allocation, or a static placement plan. |
| Abstract handoff fact | A caller-supplied planning requirement represented by `Placement.AtmospherePathInputHandoff`, `Placement.CommandReplicaHandoff`, or `Placement.AcquisitionOutputHandoff`. It declares the relevant subject, payload byte count, finite maximum in flight, and provenance, but allocates no handoff and is not a `Plant.PreparedCrossDomainHandoff` or a transfer. |
| Acquisition-output disposition | The placement-policy declaration for one complete acquisition group's output: `Placement.DeviceReadyOutput` keeps it device-ready, while `Placement.ExplicitConsumerOutput` names both the consumer execution resource and consumer memory domain. Both retain explicit resource criticality; there is no implicit host fallback. |
| Placement policy input | `Placement.PlacementPolicyValues` is the immutable, canonically ordered set of hard constraints, deterministic preferences, explicit assignments, and acquisition-output dispositions for a later planner. `Placement.PlacementInputs` composes those policy values with `Placement.PlacementFacts` and validates inventory references and memory-domain ownership only; neither is a candidate or an admitted static placement plan. |
| Structural resource fact | An immutable, versioned core record of exact array-storage bytes explicitly owned by one stable prepared logical owner on one exact compute device. It separates structural resident bytes from structural workspace bytes. A reporter enumerates its owned allocations through model dispatch; it does not walk object fields, use allocator telemetry, infer accelerator object size, count borrowed aliases, or include opaque library/runtime storage. `Plant.structural_array_bytes` counts supported explicitly owned dense storage without reading or copying its elements and fails closed for unsupported array layouts. Unsupported ownership remains an explicit unknown fact rather than a guessed byte count. |
| Structural resource owner | The stable logical prepared owner to which one structural resource fact is attributed, represented by `Plant.StructuralResourceOwnerID`. Its category and component identity follow the prepared telescope, atmosphere, optical path, acquisition, controllable optic, command endpoint, sampled aberration, or other declared owner. It is not Julia object identity, an array pointer, a task, a resource placement, or an execution-owner ordinal. |
| Structural resident bytes | The overflow-checked total byte extent of explicitly owned prepared arrays that retain immutable numerical data, mutable physical state, or caller-visible products for a run. Borrowed arrays and aliases are counted only by their nominated logical owner. Host configuration and intentionally excluded staging storage do not silently become accelerator-resident bytes. |
| Structural workspace bytes | The overflow-checked total byte extent of explicitly owned, reusable scratch arrays required by prepared execution. Workspace bytes are separate from persistent numerical state and caller-visible products even though all may remain allocated for the run. |
| Opaque resource reserve | A separate caller- or provider-supplied byte reserve for FFT plans, library work areas, allocator/runtime state, or other storage without an exact core structural-array contract. It records an exact compute device, logical owner, provider identity, and `Plant.ResourceEstimateMethod`; it never changes the structural resident or workspace totals. |
| Resource-estimate method | The deterministic identity and positive version of an algorithm or declared procedure that produces a resource-byte estimate, represented by `Plant.ResourceEstimateMethod`. Structural facts aggregated for one exact prepared graph must use one matching structural-enumeration method. Opaque reserves may use provider-specific methods. Changing enumeration, ownership, or reserve-estimation rules requires a new version of the corresponding method. |
| Group placement | The cold assignment of one stable prepared path execution-group identity to one execution resource. It is distinct from optical-plane placement, compute-device identity, and execution-owner scheduling or CPU affinity. A Gate 9A group retains its optical path and acquisition consumers on the same execution resource. |
| Static placement plan | The immutable HIL preparation result containing the resource inventory snapshot, complete-group assignments, memory domains, bounded handoffs, constraints, headroom, simultaneous-burst assumptions, reserved contexts, stable tie-breaks, planner/estimate versions, and rationale. Re-running a planner creates a new decision; the runtime does not migrate or re-plan an armed plan. |
| Execution-owner scheduling and affinity | The HIL deployment decision that binds one already placed single-writer execution owner to a long-lived Agent runner, Julia thread, and optional CPU affinity. It does not choose the group's compute device or memory domain. |
| Execution owner | One stable run-local logical owner prepared for exactly one path execution group or compatible device batch and its mutable workspace, backend, and compute device. It has exclusive write ownership, fixed group ordinals, one bounded due-work SPSC path, and one owner-specific bounded completion path. A deterministic policy may service that ownership synchronously; a threaded policy may bind it to one reusable task. `ExecutionOwnerID` is a positive run-local ordinal, not a declared optical identity, Julia task/thread affinity, compute device, RTC endpoint, transport role, or automatic placement decision. |
| Plant namespace | `AdaptiveOpticsSim.Plant`: the canonical Julia owner of HIL-neutral plant definitions and preparation, virtual plant time, schedules and triggers, detector-acquisition events, command schemas and lifecycle, illumination and providers, and serial event composition. `AdaptiveOpticsSim` exports the module itself but does not provide root compatibility bindings for its contents. Routine vocabulary is exported from `Plant`; stable advanced policies, state/workspace owners, traits, transitions, and accessors remain qualified-public. |
| Detector namespace | `AdaptiveOpticsSim.Detectors`: the canonical Julia owner of detector response and MTF, conventional frame/area sensor models, shutter and readout behavior, prepared acquisition, and detector readout products. Scheduled virtual-time acquisition events belong to `Plant`, while detector-plane optical products belong to `Optics`. |
| Atmospheres namespace | `AdaptiveOpticsSim.Atmospheres`: the canonical Julia owner of atmosphere models and state, source-direction geometry, direction rendering and batching, and atmosphere-coupled propagation. Source radiometry, optical-plane products, and general propagation remain in `Optics`; plant time and path scheduling remain in `Plant`. `AdaptiveOpticsSim` exports the module itself but provides no root compatibility bindings for atmosphere-owned names. |
| WavefrontSensors namespace | `AdaptiveOpticsSim.WavefrontSensors`: the canonical Julia owner of composed wavefront-sensor front ends, observations, measurements, detector bindings, estimators, geometric slope kernels, and LiFT. Reusable microlens arrays, masks, phase spots, and defocus elements remain physical `Optics` components. |
| Curvature channel readout | `CurvatureChannelReadout`: the packed two-branch Curvature WFS representation with one positive-defocus and one negative-defocus value per pupil sample. It may feed a fixed linear-mode APD channel bank or an explicitly arranged counting detector. The term describes the WFS-to-detector channel mapping, not a claim that every downstream detector is photon counting or an area image. |
| Calibration namespace | `AdaptiveOpticsSim.Calibration`: the canonical Julia owner of interaction and control matrices, modal bases, inverse policies, fitting and identification workflows, and model-derived NCPA synthesis. Physical NCPA storage remains in `Optics`; runtime controllers remain in `Control`. |
| Control namespace | `AdaptiveOpticsSim.Control`: the canonical Julia owner of control reconstructors, controller composition, delay lines, and prepared runtime control operations. Tomographic atmosphere reconstruction remains in `Tomography`. |
| Tomography namespace | `AdaptiveOpticsSim.Tomography`: the canonical Julia owner of guide-star geometry, atmospheric reconstruction, fitting, and DM-command projection for tomography workflows. |
| Ensembles namespace | `AdaptiveOpticsSim.Ensembles`: the canonical Julia owner of coarse offline execution policies, sweeps, and optional parallel scheduler integrations. It is not the deadline scheduler for `AdaptiveOpticsHIL.jl`. |
| Stable declared identity | An explicit typed component identity that remains attached to the same physical or logical owner when declarations are reordered. `OpticalPathID`, `AcquisitionID`, `ControllableOpticID`, `CommandEndpointID`, and `PlantCommandSchemaID` wrap symbols for the implemented plant topology and command contracts. Tuple position, task/thread identity, ring position, Julia `hash`, and device ordinal are not stable declared identities. Hashing the typed values for a cold lookup does not define, derive, or serialize their identities. |
| Plant definition | `PlantDefinition`: the immutable topology binding of one cold telescope definition and one cold timed-atmosphere definition to independent controllable-optic definitions, sampled aberrations, reusable optical-path definitions, and independent acquisition definitions. Each controllable-optic definition owns one or more immutable command schemas. The telescope and atmosphere declarations contain no prepared numerical arrays, mutable evolution state, array backend, or compute device. Where retained caller inputs satisfy the target preparation contract, the same definition can be prepared independently for distinct exact compute devices. A plant definition is not prepared execution and owns no mutable command state, schedule, RNG stream, queue, transport, or HIL descriptor. |
| Cold plant-model definition | A configuration-only value whose type explicitly returns `ColdPlantModelDefinition()` from `plant_model_definition_style`. The opt-in contract excludes prepared plans and workspaces, mutable simulation or detector state, schedules, RNG streams, queues, transport, and HIL descriptors. Unrecognized types fail closed. |
| Preparation | The cold phase that validates configuration and binds it to concrete storage, array backend, compute device, plans, workspaces, and exact ownership relationships before repeated execution. A `prepare_*` function may allocate and plan; its corresponding warmed `!` operation reuses the prepared state. Preparation is distinct from simulation initialization that evolves physical state. |
| Optical-path definition | `OpticalPathDefinition`: an explicitly identified source and opted-in cold optical-model declaration that can be prepared once and reused by compatible acquisitions. It owns no propagation workspace or acquisition state. |
| Acquisition definition | `AcquisitionDefinition`: an explicitly identified, opted-in cold acquisition-model declaration plus a reference to one `OpticalPathID`. It is independent of the path definition and carries no schedule or prepared mutable acquisition state. |
| Controllable-optic definition | `ControllableOpticDefinition`: an explicitly identified, opted-in cold declaration of one physical controllable optic, one required optical placement, one required path-visibility declaration, and one or more immutable `PlantCommandSchema` values for independently timed or latched command surfaces. It owns no mutable command/optic state, timing calendar, prepared optical execution group, or HIL descriptor. A device with several endpoint schemas is still one physical optic; several optics never become one device merely because they are co-conjugated. |
| Deformable-mirror plant model | `Plant.DeformableMirrorModel`: the cold, configuration-only native DM model used inside a `ControllableOpticDefinition`. It fixes actuator topology, influence and actuator-response models, device-internal actuator `Misregistration`, numeric type, and pupil-relay registration without owning a live `DeformableMirror`, command buffer, sampled surface, workspace, schedule, or transport. Plant preparation binds it to the prepared telescope grid and exact plant target, immutable influence data, and separate active/staged DM runtimes. |
| Controllable-optic path visibility | The immutable declaration of which plant optical paths contain one physical controllable optic. `AllPathVisibility()` selects every declared path; `SelectedPathVisibility` owns a nonempty duplicate-free tuple of stable `OpticalPathID` values that must resolve in the containing plant. Visibility is independent of optical placement, command timing, transport, and execution-resource placement. |
| Command-endpoint identity | `CommandEndpointID`: the stable declared identity of one independently timed or latched command surface owned by exactly one `ControllableOpticDefinition`. It is not a payload schema, queue, port, atomic transaction, clock domain, or prepared mutable endpoint. |
| Command-endpoint configuration | `CommandEndpointConfiguration`: the run-configuration value that binds one declared endpoint to bounded calendar/history capacities, an initial effective command, and an optional safe command. It does not select storage placement or declare cadence, transport, optical placement, grouping, or transaction membership. Plant preparation derives array-command storage from the exact plant target and defensively copies array-valued initial and safe commands; scalar command values remain host-resident. |
| Plant-command schema | `PlantCommandSchema`: the immutable, versioned semantic contract for values presented to one `CommandEndpointID`. It fixes exact scalar or array element type and dimensions, physical-unit and sign-convention identities, basis and basis revision, absolute or incremental meaning, bounds, and value/sequence/effective-time/silence policies. It contains no mutable sequence state, admission calendar, effective value, session, external-clock mapping, payload lease, queue, transport, or outcome. `PlantCommandSchemaID`, `PlantCommandSchemaVersion`, and `CommandBasisRevision` are explicit process-stable values; Julia object identity and `hash` are not revisions. |
| Controller-output product | One named caller-owned scalar or fixed-shape array produced by a controller for a physical command endpoint. An array may be a view into a larger controller-owned buffer. Its name is a semantic identity, not a packed-buffer offset, endpoint timestamp, or transaction group. |
| Prepared controller-output routing | `PreparedControllerOutputRouting`: a cold, zero-copy binding from every named controller-output product to one distinct prepared command endpoint. Preparation requires exact numeric type, shape, array backend, and compute-device compatibility; scalar products use assigned `Ref` storage. A route owns no command sequence, effective time, admission, transaction, queue, transport, optical grouping, or payload copy. |
| Plant command | `PlantCommand`: one immutable `AdaptiveOpticsSim.Plant` presentation value carrying the target endpoint and exact schema/version identities, positive endpoint-local command sequence, requested plant-effective timestamp, and scalar or fixed-shape payload. It carries no run/session identity, external timestamp, mapping version, lease, ring position, or transport metadata. Its caller-owned payload is borrowed only for the admission call and copied on successful admission. |
| Command presentation | One attempt to admit a plant command to its prepared endpoint. The endpoint assigns a positive `CommandPresentationID`, so retries of the same command sequence remain distinct attempts with distinct terminal-disposition credit. A programming error before a valid presentation call is not a command presentation. |
| Absolute command | A plant command whose complete fixed-shape payload denotes the requested endpoint value in the declared basis. For such an endpoint, replacing the prior value is absolute semantics, not a third *replacement* semantic. Partial or sparse updates require another explicitly defined payload schema. |
| Incremental command | A plant command whose payload denotes a change to be applied to the endpoint's effective held value in the declared basis. Effective-value range validation may therefore require application state and cannot always be completed when the payload is first presented. Pending incremental deltas cannot use lossy older-command supersession; they require preservation or a separately specified accumulation policy. |
| Effective command | The complete currently held endpoint value in its declared command basis after absolute replacement, incremental accumulation, application-stage policy, or an explicit safe-command transition. It is command state, not necessarily an instantaneous physical optic surface: a device model may separately impose response dynamics such as slew, settling, hysteresis, or bandwidth. |
| Plant-command payload validation | Cold semantic compatibility checking performed by `validate_plant_command_payload`. It checks exact scalar/array type and shape, finite values, and any presentation-stage range policy without mutation. It does not admit, sequence, schedule, clip, apply, or produce a terminal model disposition; those are distinct later operations. |
| Command range stage | `ValidateOnPresentation` means bounds apply directly to the presented payload. `EnforceOnApplication` defers the bound check until the command is combined with effective state, as may be required for an incremental command. `ClipInvalidCommand` declares later clipping but `validate_plant_command_payload` never mutates caller storage. Nonfinite values cannot be clipped. |
| Command sequence policy | The endpoint's declared handling of sequence anomalies. The first successfully admitted sequence establishes the endpoint baseline. A duplicate repeats an accepted sequence still in the prepared window; stale is older than that retained admissible history; reordered arrives behind a newer sequence but remains within the window; skipped advances across absent sequences. Duplicate and stale values cannot be accepted as new commands. Only successful admission enters the fixed modulo history, so a capacity/time rejection may be retried with the same command sequence as a new presentation. |
| Command effective-time policy | The endpoint's declared handling of a command whose effective time is future or already late, plus whether a new absolute pending command preserves or explicitly supersedes older pending commands. Future commands occupy a fixed-capacity sorted calendar. Late apply-now preserves the requested timestamp, schedules at current plant time, and records lateness; it never backdates state. The API distinguishes the requested effective, scheduled, application-ready, and terminal timestamps rather than calling each one *effective* or *application* time. Every rejected or superseded presentation receives a terminal disposition. External timestamp mapping precedes this core policy. |
| Prepared command endpoint | `PreparedCommandEndpoint`: the run-immutable binding of one exact schema to positive active capacity, accepted-sequence window, stable ordering ordinal, and payload-storage backend. Scalar payload slots require `Backends.CPUBackend()` and remain host-resident; fixed-shape array slots use the selected array backend. Its separate `CommandEndpointState` owns fixed payload slots, compact metadata, sequence and admission-age history, a sorted future calendar, and terminal failure state; its caller-owned `CommandDispositionWorkspace` holds unconsumed terminal credits. It may be exercised directly or owned by a prepared plant event loop. |
| Command application state | The qualified mutable `CommandApplicationState`: the single-writer owner of one endpoint's effective command, transactional array staging, optional prepared safe command, application timestamp, and command-silence latch. Construct exactly one for an exact endpoint-state owner, with an explicit initial effective command, before that owner first admits a command. It is not a physical optic, response-dynamics model, scheduler, or HIL watchdog. |
| Application-ready command claim | `PlantCommandApplicationClaim`: the opaque bounded single-writer claim that removes the earliest due command from the pending calendar and borrows its endpoint-owned payload read-only for application. Its scheduled timestamp remains distinct from the instant at which it became application-ready. Only one claim may be outstanding. `apply_claimed_plant_command!` combines it with effective command state and reports one terminal disposition; the claim itself does not assert successful application or mutate a physical optic. |
| Terminal model disposition | Exactly one core terminal outcome for a command presentation: rejected during admission or application, superseded while pending, applied after its claim, or failed during admission, application, or drain. `PlantCommandDisposition` retains endpoint, sequence, requested and terminal plant timestamps, lateness, reason, and any superseding presentation. It is not the HIL boundary completion that returns a transport payload lease. |
| Composed command-admission frontier | The latest canonical plant instant at which a command may be routed into a prepared event loop without crossing its next unprocessed event. The initial timestamp and unprocessed instants no later than that event are admissible; a timestamp already processed by any event phase is not. This is a causality boundary for event-loop admission, not the command's requested effective timestamp or a transport queue limit. |
| Prepared controllable optic | `PreparedControllableOptic`: the immutable binding of one declared physical optic to model-specific preparation data and its independent prepared endpoint slots. Each separately constructed single-writer state receives fresh state-owned copies of array-valued initial commands and owns visible and staged physical response; a separately constructed workspace owns scratch. Staging and publication receive the exact plant-effective timestamp so a physical model can preserve time-dependent state. A successful `stage_controllable_optic_command!` must make the corresponding `commit_controllable_optic_command!` a bounded, nonthrowing publication step. |
| Prepared controllable-optic path bindings | `PreparedControllableOpticPathBindings`: the bounded preparation-time resolution of declared visibility into canonical path offsets, visible-optic slots, and co-placed plane groups. Paths and optics are ordered by stable declared identity, not declaration order, Julia `hash`, task identity, or device ordinal. A warmed path uses its direct binding range instead of testing a set or scanning every optic. |
| Prepared controllable-optic plane group | `PreparedControllableOpticPlaneGroup`: one contiguous group of distinct visible optics that share an optical placement on one prepared path. Its representative and path slots are run-local references only. Grouping enables one later placement transform followed by several independently held surfaces; it does not synchronize endpoints, imply an atomic transaction, or prescribe CPU/GPU placement. |
| Atomic plant-command transaction | `PlantCommandTransaction`: an explicit all-or-none command group containing at least two endpoints on distinct physical optics, with one common requested and resolved plant-effective timestamp. Every member endpoint must preserve pending commands. Admission preflights and stages every payload before mutating any endpoint calendar; application stages every effective command and physical response before publishing any member. Atomicity is never inferred from equal timestamps, a packed vector, shared placement, or co-conjugation. |
| Co-conjugated optics | Distinct controllable optics whose modeled surfaces act at the same optical conjugate and therefore add optically while retaining independent command state and timing. Preparation groups compatible path-local couplings separately for each visible path and preserves stable optic-identity order. A path-local autonomous optic retains its separate exact coupling. The group shares geometry only; it does not share surface or command state. |
| Autonomous periodic optic | A path-local controllable optic whose bounded setpoints parameterize a locally generated periodic waveform instead of carrying one command per waveform point. `AutonomousPeriodicOpticDefinition` binds one such optic to one optical path, one run-immutable fidelity policy, and one waveform phase reference. It owns no RTC transport or wall clock. |
| Waveform phase reference | The plant-time origin used to evaluate an autonomous waveform. `FreeRunningPhaseReference` uses a configured origin, `TriggerSourcePhaseReference` follows realization of a declared trigger source, and `TriggerResetPhaseReference` follows physical delivery to one declared consumer after its link delay, skew, jitter, drop, or duplication. A reported timestamp-label offset does not move the physical phase reset. |
| Cycle-averaged modulation fidelity | `CycleAveragedModulationFidelity`: one normalized optical quadrature over a complete periodic cycle at one frozen optical epoch. It is invariant to instantaneous waveform phase and frequency, so those setpoints remain device state without changing the full-cycle optical average. Detector acquisition, not the quadrature, integrates exposure time. |
| Plant-time command silence | The replayable model condition in which a command endpoint has received no qualifying admission or application for its declared age interval. `CommandSilencePolicy` declares indefinite hold, safe-command, or fail behavior, its admission/application age origin, and any positive timeout. Before the first qualifying event, the endpoint's configured initial timestamp is the common age baseline; thereafter the selected successful admission or effective application rebases it. Execution-clock ingress liveness remains a separate HIL lifecycle concern. |
| Command-silence transition | `PlantCommandSilenceTransition`: the value record of one exact safe-command or terminal fail transition, including endpoint, action, selected age origin, origin timestamp, deadline, and transition timestamp. Direct endpoint execution changes only effective command state; composed execution stages and publishes the safe physical response before exposing it. A fail transition drains pending presentations and terminally fails the endpoint. A due command at the same plant timestamp is resolved first. |
| Topology registry | A fixed-size, canonically ordered homogeneous collection of declared or prepared plant owners whose cardinality is a value rather than part of the Julia container type. Access crosses a bounded per-owner function barrier into a concrete small pipeline. A topology registry is not a schedule, work queue, transport, dynamically resizable collection, or claim that every owner has the same concrete implementation. |
| Prepared plant | `PreparedPlant`: the schedule-free result of `prepare_plant(definition, target; ...)` for one exact compute device. It owns that target and its retained prepared device execution context, one independently materialized numerical telescope and timed atmosphere, fixed-size topology registries of prepared controllable optics, command endpoints, sampled aberrations, path executors, acquisition owners, and owner-bound RNG groups, plus bounded path-to-optic and path-to-aberration bindings. Every prepared data-plane array in the owned graph must reside on the exact target; scalar command values, host configuration and registries, and deliberate host RNG staging are not data-plane residency violations. `Backends.compute_device(plant)` reports the target; `plant_definition`, `prepared_telescope`, and `prepared_atmosphere` expose the corresponding definition and numerical owners. Registry cardinality does not enter the prepared plant type; each owner's small numerical pipeline remains concrete behind a function barrier. The plant does not advance the atmosphere, decide due work, own a clock, or publish through a HIL port. Every declared optic and endpoint requires explicit model preparation and endpoint run configuration; preparation never silently omits a device. |
| Prepared path executor | `PreparedPathExecutor`: the single-writer owner of one frozen source, exact plant-atmosphere binding, path-local pupil-function, declared-plane field, or intensity input, prepared input-materialization operation, acquisition-facing photon-rate result, and concrete prepared optical execution state. It retains the plant's exact prepared device execution context, including its backend stream where applicable. Public path materialization and execution enter that context, complete its backend stream, and then restore the caller's previous device and stream selections. Its result may be borrowed read-only by several acquisitions. |
| Calibration illumination | Illumination used in a calibration scenario. It is an application role, not a privileged source technology, optical propagation mode, detector mode, or control authority. It enters an ordinary prepared path at an explicitly declared boundary. |
| Illumination entry boundary | The typed location/product contract at which a prepared illumination evaluator writes a caller-owned `PupilFunction`, `ElectricField`, or `IntensityMap`. The boundary excludes upstream optics by construction; it does not request that core bypass named components. |
| Prepared illumination entry | `PreparedIlluminationEntry`: a qualified-public schedule-free path materializer binding one entry tag, exact caller-owned payload, immutable evaluator wrapper, separate single-writer state/workspace, defensive visibility and payload contracts, explicit combination semantics, plant time, and a path-owned `:illumination` RNG stream. It is not an acquisition, scheduler, transport, or universal optical graph. |
| Downstream visibility | An application-owned description of which declared optical branches may consume a product or see an optic. The Gate 2 illumination seam snapshots this value but does not interpret topology; later placed-optics preparation validates physical visibility. |
| Acquisition product contract | `AcquisitionProductContract`: the run-immutable compatibility snapshot for one caller-owned `AcquisitionProducts` destination. It covers observation and measurement shape, numeric type, backend/device, typed units and metadata, and required acquisition-level metadata. That metadata carries any geometry, radiometry, layout, or semantics not already present in the typed products. A provider mutates and returns the exact destination; the contract is not a HIL descriptor, lease, or transport schema. |
| Acquisition product provider | A prepared per-acquisition implementation selected as full optical, command-responsive reduced order, or nonresponsive synthetic/replay through `acquisition_provider_style`. Every provider writes the same logical acquisition product contract. Provider selection is run-immutable; a different fidelity requires another preparation. Its `acquisition_provider_payload_work` declaration describes payload work but is not latency, throughput, cache-residency, or optical evidence. |
| Acquisition lifecycle | The explicit virtual-time transitions that turn a periodic or delivered-trigger start into one complete acquisition product. A cold `AbstractAcquisitionLifecycleDefinition`, immutable `AbstractPreparedAcquisitionLifecycle`, and separately owned mutable `AbstractAcquisitionLifecycleState` distinguish declaration, prepared parameters/workspace, and single-writer run state. Detector and intentional direct-measurement lifecycles share this boundary without implying the same physical transformations. |
| Acquisition event definition | `AcquisitionEventDefinition`: the binding of one prepared acquisition identity to one acquisition lifecycle and one periodic or delivered-trigger start source. It is intentionally broader than a detector event because an intentional direct measurement has exposure and readiness semantics without a fictitious detector. |
| Direct-measurement acquisition | `DirectMeasurementAcquisitionDefinition`: a scheduled lifecycle that time-averages a held instantaneous `WFSMeasurement` over a half-open exposure, then applies explicit readout-completion and readiness delays. It does not create a detector observation, photon-arrival-rate product, detector noise, rolling shutter, frame transfer, or progressive readout. |
| Harmonic disturbance model | `HarmonicDisturbanceModel`: a deterministic time-correlated modal sequence evaluated from explicit plant time as an offset plus one sinusoid per disturbance coordinate. Equal parameters and timestamps replay exactly on the same numerical backend and runtime. It is a bounded validation disturbance family, not an atmospheric-turbulence equivalence claim. |

Lifecycle observations that are compared as execution-clock coordinates carry this identity; matching raw nanosecond values from different identities are not interchangeable. It is not object identity, a wall-clock epoch, or a synchronization claim. |
| Cached execution clock | A worker-readable monotonic execution clock refreshed from another monotonic source by one prepared update owner. Its configured refresh cadence and maximum observed staleness are run evidence. Workers receive a read-only view; they do not refresh the cache or use an epoch clock for pacing. |
| Execution-clock update owner | The single prepared logical owner allowed to refresh one cached execution clock. Its stable identity belongs in run metadata. An identity is an ownership contract, not a transport role or a substitute for deployment-level thread placement. |
| Run/session identity | A positive run-local epoch shared by every HIL port, pool, readiness observation, lifecycle event, and terminal record participating in one prepared run. A subsequent run receives a fresh identity and generation state. It is not plant time, an execution-clock coordinate, a process identifier, or a transport session. |
| Arm window | The bounded execution-clock interval for one operational arm attempt, from its opening coordinate through its inclusive arm deadline. Readiness at the exact deadline is admissible; the first later observation expires the attempt. Elapsed comparisons follow the execution clock's signed modular rule and remain valid only for intervals shorter than `2^63` nanoseconds. |
| Adapter readiness | A transport-neutral, same-run observation supplied by user orchestration that the selected external RTC adapter is ready for the run to begin. It carries an execution-clock identity, status, and observation coordinate, but no socket, client/server, discovery, reconnect, or health-protocol semantics. It is distinct from detector acquisition readiness and complete-product readiness. |
| Run termination | An immutable operational record distinguishing a clean stop request or configured terminal event from arm or runtime failure. Recording termination does not by itself prove that ports are closed, ownership is drained, or every owner has acknowledged shutdown; those require separate bounded-shutdown evidence. |
| External timestamp domain | One stable RTC, camera, or device timestamp coordinate. It is mapped into canonical plant time before ordering, latency calculation, port transfer, or core admission. A timestamp domain is not a device cadence, trigger source, execution clock, or wall-clock synchronization algorithm. |
| Timestamp-domain mapping | One immutable affine correspondence from an external timestamp domain into plant time, identified by a positive mapping version and carrying source and plant anchors, a positive exact rational rate, uncertainty, and an inclusive source validity interval. Conversion uses checked integer arithmetic and round-to-nearest, ties-to-even; no floating-point timestamp controls ordering. |
| Timestamp mapping version | A positive, domain-local version identifying the exact timestamp-domain mapping applied to one boundary observation. Versions increase prospectively. Installing a later version does not modify, reorder, or retimestamp any prior mapped descriptor or admitted event. |
| HIL execution time | Host-side time at which simulation work runs. It is distinct from model time and reported detector timestamps. |
| Command submission descriptor | A HIL-boundary descriptor that correlates one transferred payload lease and external timing metadata with a prepared command endpoint. Enqueueing the descriptor transfers ownership but does not imply plant-command admission or application. |
| Command outcome | A HIL-boundary completion that returns the submission credit and reports the correlated core model disposition plus boundary timing and failure metadata. It is not sampled device feedback. |
| Payload lease | A generation-checked immutable reference that grants one prepared logical owner exclusive access to a caller-supplied payload slot. A successful handoff transfers the lease; full, closed, stale, foreign, duplicate, and rejected operations retain the ownership stated by their resource policy. |
| Lease-return path | The bounded SPSC handoff from one payload consumer back to that payload pool's single owner. A successful release queues the lease for owner reclamation; it does not let the consumer directly make producer storage reusable. |
| Reserved return credit | One usable lease-return descriptor slot reserved for each payload slot that may be consumer-leased simultaneously. A valid first release from the current session therefore cannot encounter ordinary full backpressure; return-path full is an invariant failure and leaves the lease consumer-owned. |
| Port lifecycle state | The cold state derived from one bounded port's close flag and descriptor occupancy: **accepting** permits new producer transfer, **draining** rejects new transfer while published descriptors remain consumable, and **drained** is closed with no published descriptor remaining. Closing a port does not revoke payload leases already transferred through it. |
| Payload-pool lifecycle state | The cold state of producer claims for one prepared payload pool: **accepting** permits a new claim, **draining** rejects new claims while at least one slot remains producer-owned, queued, consumer-leased, or return-queued, and **drained** is closed to claims with every slot reclaimed. Claim closure precedes lease-return-path closure so no future legal lease can lose its reserved return path. |
| Resource full policy | The prepared, resource-specific action when bounded capacity is unavailable: retain producer ownership and report full, reclaim a newly completed droppable product and report full, or treat full as a violated reserved-capacity invariant. It never creates an implicit unbounded retry backlog. |
| Resource criticality | The run-immutable classification of one command endpoint, acquisition endpoint, execution owner, bounded payload resource, or observation tap as **required** or **optional**. A required resource cannot shed work when its prepared capacity or deadline contract is missed. Optional does not mean lossy: loss is legal only when a separate prepared full/stall policy permits it. |
| Overload recovery threshold | The prepared occupancy below the corresponding overload threshold at which bounded runtime accounting records that one overload episode ended. Reaching it does not restart a failed run, prove lease/sequence recovery, or authorize a provider/fidelity change. |
| RTC-ingress-liveness watchdog | An optional HIL operational watchdog in one identified execution-clock domain. Its initial origin is entry into `RunRunning`; only successful semantic command admission resets it. Its deadline is inclusive, so an admission observed exactly at the deadline may reset it and the first later observation expires it. Expiry fails the run without changing effective command or physical optic state and remains distinct from plant-time command silence and transport health. |
| Ownership deficit | A bounded terminal accounting result identifying prepared payload slots that are not free after publication has ended and the declared drain has completed. State-specific counts distinguish producer-owned, queued, consumer-leased, and return-queued slots; ordinary in-flight ownership during an active run is not by itself a failure claim. |
